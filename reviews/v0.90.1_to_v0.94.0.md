## Summary of Changes

The diff spans upstream releases v0.91 through v0.94 (two commits, 31 changed files, ~2,000 insertions of which roughly half are new tests, ~400 deletions). Both reviewers independently verified source integrity: Reviewer 1 diffed the vendored tree against the official v0.94.0 release tarball and found it byte-identical, and Reviewer 2 confirmed tracked vendored files match the official tag and that release notes corroborate the local changes. The only discrepancies are a handful of upstream test fixtures absent from the vendored copy (excluded by the sync's ignore rules), which both reviewers agree cannot introduce malicious behavior. No binary additions, executable-bit changes, hidden payloads, or unexpected symlinks were found.

The largest functional addition is a volume recreation feature: when a stack's NFS/CIFS/tmpfs-backed volume definition changes, doco-cd now force-stops and removes the stack's containers using that volume, force-removes the volume, and lets Compose recreate it with the new options. A new `volumes` scope in the recreate-ignore configuration allows opting out. Relative git submodule URLs (`../repo.git`) are now resolved against the parent repository's remote URL before cloning, matching native git semantics, with authentication recalculated for the resolved URL.

Other changes include: a new `DATA_MOUNT_PATH` environment variable (default `/data`) replacing the hardcoded data mount constant, with the implicit `VOLUME /data` directive removed from the Dockerfile; OCI artifact deployments now honoring `customTarget` from the webhook URL to select `.doco-cd.<target>.yaml` config files, mirroring existing git-source behavior; and a change to auto-discovery so that finding zero compose files returns a successful empty result, enabling cleanup of obsolete stacks. Housekeeping covers Go 1.26.3 -> 1.26.4, digest-pinned base image and GitHub Actions bumps, an Infisical SDK API adaptation, and documentation updates.

Note the operational impact of the Dockerfile change: with `VOLUME /data` removed, Docker no longer auto-creates an anonymous volume, so startup fails hard unless a volume is explicitly mounted at `/data` (or `DATA_MOUNT_PATH`). Deployment configuration should be verified before rollout.

## Dependency Review

Both reviewers agree that **no new direct dependencies were added**. All `go.mod` changes are version bumps of existing dependencies: AWS SDK, sigstore/cosign 3.0.6 -> 3.1.1, docker/cli, Infisical SDK 0.7.1 -> 0.8.0, Kubernetes libraries, golang.org/x/*, and OpenTelemetry. A handful of new module paths appear in `go.sum`, all reputable transitive additions pulled in by existing dependency trees: `filippo.io/mldsa` (post-quantum ML-DSA signatures by the Go crypto maintainer, via cosign 3.1.1), `github.com/tink-crypto/tink-go-awskms/v3` (Google-maintained, via sigstore), `github.com/go-openapi/runtime/server-middleware` (module split), `github.com/google/go-github/v88` (major-version bump of the standard GitHub client, previously v73), and `go.opentelemetry.io/otel/metric/x` (OTel experimental metrics). Reviewer 2 additionally noted that the new checksum-only modules are not imported by the changed application code. Neither reviewer found any obscure or suspicious new execution, networking, or crypto dependency; base images and CI actions remain digest-pinned.

## Security Findings

### OCI trust-policy bypass: unsigned artifacts can destroy stacks before signature verification

**Flagged by:** Reviewer 2 only; conflicting assessment with Reviewer 1.
**Severity:** High.

Reviewer 2 traced a destructive pre-verification path introduced by the auto-discovery change. The new logic in `internal/config/deploy/deploy.go` explicitly returns an empty-but-successful config list when auto-discovery finds no compose files. For OCI webhooks, the artifact is pulled and extracted and its deployment configuration parsed (including auto-discovery) *before* any deployment stage runs; reconciliation then unconditionally runs obsolete-stack cleanup ahead of the deployment stages, and with an empty desired set, cleanup destroys matching previously auto-discovered stacks. OCI signature verification only occurs inside stage 1 per deployment config — with zero configs, no stage and therefore no verification ever runs. An attacker able to publish an unsigned artifact to a watched OCI source could supply just `auto_discovery: enabled: true` with no compose files: even though the global trust policy would ultimately reject the artifact, cleanup would first remove containers/services, images by default, and volumes if the previous deployment enabled `remove_volumes`. Reviewer 2 notes this defeats the protection added for GHSA-5rv3-qpp3-6jp5 through a different pre-verification side effect, and that the new integration test confirms empty-config-list stack removal but does not cover an unverified OCI source. The required fix is to verify the resolved OCI digest before parsing artifact configuration, running auto-discovery, or invoking any reconciliation cleanup.

Reviewer 1 did not identify this interaction — the underlying change was characterized only as a housekeeping bugfix ("auto-discovery with zero compose files returns an explicit empty result") and Reviewer 1's report concludes no backdoors or blocking issues exist.

**Assessment:** This is a genuine conflict, and Reviewer 2's position is more convincing. Reviewer 2 provides a concrete, file-and-line-level execution trace (extraction -> config parse/auto-discovery -> unconditional cleanup -> verification only in stage 1), identifies the exact attacker capability required, and ties the finding to a previously patched advisory. Reviewer 1 does not rebut this reasoning — the interaction between the empty-result change and pre-verification cleanup simply was not analyzed in that report. An unrebutted, well-evidenced trust-boundary bypass with destructive effect should be treated as a real High-severity risk. It is mitigated only if no unauthenticated/unsigned party can publish to the watched OCI sources in the target environment.

### Volume mount credentials can enter debug logs

**Flagged by:** Reviewer 2 only.
**Severity:** Medium.

The new volume recreation path in `internal/docker/volumes.go` logs the complete existing and desired `DriverOpts` maps when comparing volume configurations. CIFS mount options commonly contain inline `username=` and `password=` values, and resolved Compose interpolation can also place secrets there. With debug logging enabled, those credentials would be written to container logs or centralized log storage. The image defaults to `LOG_LEVEL=info`, so nothing is exposed by default.

**Assessment:** Real but conditional risk. The reasoning is sound — secret-bearing driver options are logged verbatim — but exposure requires debug logging to be enabled and secret-bearing volume options to be in use. Reviewer 2's recommendation stands: redact or remove the options from log output upstream, and until then avoid debug logging in environments using credentialed volume mounts.

### Destructive volume recreation operations

**Flagged by:** Both reviewers, in agreement.
**Severity:** Low (by design).

`removeMismatchedRecreatableVolumes` runs on every deploy and can force-remove containers and volumes. Both reviewers found it well-scoped: it only targets volumes labeled as belonging to the stack being deployed, and only `local`-driver volumes of type `nfs`/`cifs`/`tmpfs` whose configuration diverges — types where the data lives remotely or is ephemeral. Reviewer 2 additionally noted it grants no new Docker permission; it exercises the already-mounted Docker socket more aggressively.

**Assessment:** Not a vulnerability — this is the intended feature and the one genuinely new privileged behavior in the release. Real data-loss exposure is minimal given the volume-type scoping, but operators should be aware deploys can now remove containers and volumes automatically.

### Relative submodule URL resolution

**Flagged by:** Both reviewers, in agreement.
**Severity:** Informational.

Resolved relative submodule URLs stay on the parent remote's host, and credentials are chosen by the existing per-host authentication resolver. A repo owner could point `../../other/repo.git` at another repository on the same git host and have doco-cd clone it with its configured token, but this exactly matches native `git submodule update` semantics, and anyone able to push to a deployed repo already controls what runs on the host.

**Assessment:** No new trust boundary is crossed and no new cross-host credential routing was found by either reviewer. No action needed.

### `customTarget` interpolated into the OCI config filename

**Flagged by:** Reviewer 1 only.
**Severity:** Informational.

`customTarget` comes from an authenticated webhook URL path segment and is formatted into the `.doco-cd.<target>.yaml` filename. A caller who already holds the webhook secret could in theory use encoded slashes to make the config lookup stat a YAML file outside the artifact directory. This mirrors the long-standing pattern used by the git source path, requires webhook authentication, and only influences which config file the deployment machinery reads. Reviewer 2 did not flag this but did confirm the OCI target support does not restore any artifact-controlled `oci.verify: false` override.

**Assessment:** Theoretical and pre-existing in pattern; negligible added risk.

## Reviewer Agreement

The reviewers agreed on source integrity (vendored code matches upstream v0.94.0), the absence of new direct dependencies or suspicious transitive ones, the safe scoping of the volume recreation feature, the benign nature of the relative submodule URL resolution, and the absence of backdoors, exfiltration paths, new endpoints, or hidden payloads. They diverged sharply on one point: Reviewer 2 identified a High-severity OCI trust-policy bypass in the auto-discovery empty-result change, which Reviewer 1 had classified as a routine bugfix and did not analyze for its interaction with pre-verification stack cleanup — leading to opposite verdicts (Reviewer 1: safe to deploy; Reviewer 2: do not deploy until fixed). Reviewer 2 also uniquely flagged credential leakage in debug logs, while Reviewer 1 uniquely noted the theoretical `customTarget` filename interpolation.

## Verdict

**UNSAFE** — Reviewer 2's High-severity finding that unsigned OCI artifacts can trigger destructive stack cleanup before signature verification is supported by a concrete execution-order trace, undermines a previously patched security advisory (GHSA-5rv3-qpp3-6jp5), and is unrebutted by Reviewer 1, who did not examine that code path. Building the image for investigation is reasonable, but deployment into the privileged environment should be blocked until upstream verifies OCI digests before configuration parsing and reconciliation cleanup (or the deployment demonstrably has no exposure to unsigned OCI sources).
