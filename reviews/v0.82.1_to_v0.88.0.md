## Summary of Changes

This update spans six upstream releases with approximately 180 files changed (~14.8K lines added, ~2.8K removed). The `internal/config` package was reorganized into `config/app`, `config/deploy`, and `config/poll` sub-packages. Major new features include a cron-based job scheduler (`internal/scheduler/`) that discovers Docker containers and services with doco-cd job labels and executes them on schedule, and an event-driven reconciliation system (`internal/reconciliation/`) that replaces the previous interval-based polling approach with Docker event subscriptions, complete with rate limiting and self-restart suppression.

New authentication and secrets capabilities were added: GitHub App installation token authentication via JWT (`internal/git/githubapp/`), domain-scoped Git credentials via `GIT_AUTH_DOMAINS` with wildcard subdomain matching (`internal/git/auth.go`), and 1Password Connect Server integration as an alternative to the service account SDK (`internal/secretprovider/1password/`). A new graceful shutdown framework (`internal/graceful/`) coordinates server lifecycle and signal handling.

Additional changes include container one-off execution for job scheduling (cloning existing container/service configs into temporary auto-removing instances), registry digest comparison for detecting upstream image changes, enhanced auto-discovery with configurable scan depth and nested config file merging, new API endpoints for job listing and triggering, and minor Dockerfile updates (Go 1.26.2 to 1.26.3, riscv64 added to Bitwarden exclusion list).

## Security Findings

### 1. Global GitHub App Credentials Sent to Arbitrary Git Hosts

**Severity: High**

**Flagged by:** Reviewer 2 (Codex). Reviewer 1 examined the same GitHub App auth code but assessed it as Low risk, focusing on the token generation mechanics and domain wildcard matching correctness rather than the global fallback behavior.

When `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY` are configured globally (without domain-scoped `GIT_AUTH_DOMAINS`), the `ResolveAuthConfig` function attaches the GitHub App config as fallback credentials for any HTTP(S) Git URL. If a deploy config specifies a `repository_url` pointing to an attacker-controlled host, the auth flow will:

1. Fall back to global GitHub App credentials (`auth.go:135`)
2. Use those credentials for the non-SSH URL (`auth.go:302`)
3. Build an API base URL from the arbitrary repository host (`resolver.go:281`)
4. Send an `Authorization: Bearer <GitHub App JWT>` header to that host (`resolver.go:251`)

The private key itself is not transmitted, but the signed JWT (valid for up to 9 minutes) can be replayed against GitHub's real API to access app-level endpoints and potentially mint installation tokens for any installation the app has access to.

**Assessment:** Codex's finding is convincing. The code path is concrete and the attack scenario is plausible — a malicious or compromised deploy configuration could exfiltrate a GitHub App JWT to an external host. Reviewer 1's analysis of the domain wildcard matching and token caching was correct but did not consider the scenario where no domain-specific match exists and the global fallback applies to an arbitrary host. This is a real credential leakage vector when global GitHub App auth is configured.

**Fix direction (per Codex):** Do not apply global GitHub App credentials to arbitrary hosts. Restrict GitHub App auth to `github.com`, `www.github.com`, known GitHub Enterprise hosts, or explicitly configured `GIT_AUTH_DOMAINS` entries.

### 2. Event-Driven Reconciliation Adds Execution Surface Area

**Severity: Low-Medium**

**Flagged by:** Both reviewers.

The new event-driven reconciliation system subscribes to Docker events and can automatically restart containers or trigger full redeployments. Both reviewers identified this as the most complex new feature. Safety mechanisms are in place: rate limiting via `RestartLimit`/`RestartWindow`, self-restart suppression, stack deployment tracking, per-stack locking via `TryLock`, explicit skipping of stacks with `destroy.enabled = true`, and a whitelist of supported events (`die`, `destroy`, `update`, `stop`, `kill`, `oom`, `unhealthy`).

**Assessment:** Both reviewers found the safety mechanisms well-implemented. The risk is inherent to the feature's design rather than an implementation flaw. This warrants ongoing attention but is not a deployment blocker.

### 3. Job Scheduler and API Endpoints as Privileged Execution Surface

**Severity: Low**

**Flagged by:** Both reviewers (Reviewer 2 emphasized the privilege implications more strongly).

The scheduler can restart containers or clone them as one-off jobs based on Docker labels (`cd.doco.job.enabled=true`). The new API endpoints (`/api/jobs`, `/api/job/{jobName}/run`) are protected by the existing API key authentication. Reviewer 2 noted that the API secret should be treated as equivalent to full Docker-host control in highly privileged deployments.

**Assessment:** This is by design. The `jobName` path parameter is used as a map lookup key against discovered containers, not in shell commands or file paths. Authentication is properly enforced. The elevated privilege characterization from Reviewer 2 is a valid operational note but not a code-level vulnerability.

### 4. Container One-Off Execution Inherits Full Source Configuration

**Severity: Informational**

**Flagged by:** Reviewer 1. Reviewer 2 mentioned this briefly.

`RunContainerOneOffFromExisting` and `RunSwarmOneOffFromService` clone the entire container/service config (environment variables, volumes, host bindings) into temporary instances. The temporary resources set `AutoRemove: true` and `RestartPolicy: "no"`.

**Assessment:** No privilege escalation beyond the source container. This is the intended behavior for job execution.

### 5. Registry Digest Lookup Adds Outbound Credential-Bearing Requests

**Severity: Informational**

**Flagged by:** Reviewer 2 only.

The new image digest comparison logic sends outbound HTTP(S) HEAD requests to container registries, including bearer-token authentication to registry auth realms. Reviewer 2 noted this is another outbound credential-bearing path, though Docker pulls already contact registries with the same credentials.

**Assessment:** Not a new risk category since Docker pulls already perform equivalent operations, but worth noting as an additional code path that handles registry credentials.

### 6. Path Sanitization, Config Merging, and File Access Controls

**Severity: Low**

**Flagged by:** Reviewer 1 only.

Compose file path validation rejects absolute paths and path traversal, validates resolved paths stay within the working directory. Auto-discovery nested config merging uses an allowlist (`doco:"allowOverride"`) to control which fields can be overridden. Protected fields (`repository_url`, `reference`, `auto_discovery`, `git_depth`) cannot be overridden by nested configs. The `#nosec G304` annotation on `os.ReadFile` is appropriate given the application's trust model for repository content.

**Assessment:** These controls are correctly implemented and consistent with the application's security model.

### 7. GitHub App Token and 1Password Secret Handling

**Severity: Low**

**Flagged by:** Both reviewers.

GitHub App tokens are cached in-memory with mutex protection and a 30-second renewal buffer. No tokens are logged or persisted to disk. The 1Password Connect integration explicitly disables the Jaeger global tracer and stores secrets in-memory only with configurable TTL. Cache is disabled in Connect mode since the Connect Server handles its own caching.

**Assessment:** Standard credential handling patterns. No persistence or logging concerns.

### 8. Deployment Skip Logic Bug Fix

**Severity: Informational**

**Flagged by:** Reviewer 1 only.

The `shouldSkipDeployment` check was inverted: `ignoredInfo.IsNeedSignal()` was changed to `!ignoredInfo.IsNeedSignal()`, correcting a bug where deployments were skipped when signals were needed (wrong) instead of when they were not needed (correct).

**Assessment:** A correctness fix with no security implications.

## Reviewer Agreement

Both reviewers agreed that the dependency additions are clean, the 1Password integration is properly implemented, the reconciliation safety mechanisms are sound, API endpoint authentication is correctly enforced, and no backdoors or data exfiltration risks were present in the diff. They diverged on a single critical point: the GitHub App credential scoping. Reviewer 1 examined the GitHub App auth code in detail but assessed it as Low risk, focusing on the correctness of token generation, caching, and domain wildcard matching. Reviewer 2 identified a specific attack path where globally configured GitHub App credentials fall through as a default to arbitrary repository hosts, allowing JWT exfiltration — a vector Reviewer 1 did not address. Reviewer 2 also placed stronger emphasis on the operational privilege implications of the job scheduler API, characterizing the API secret as equivalent to Docker-host control.

## Verdict

**SAFE WITH NOTES** — The codebase changes are well-structured with no backdoors, data exfiltration, or unexpected privilege escalation, and all dependencies are legitimate. However, deployments that use global `GITHUB_APP_ID`/`GITHUB_APP_PRIVATE_KEY` configuration (without domain-scoped `GIT_AUTH_DOMAINS`) are exposed to the JWT leakage vector identified by Reviewer 2, where an attacker-controlled `repository_url` could capture a short-lived GitHub App JWT. If GitHub App auth is in use, apply host-scoping restrictions before deploying; if it is unused, this update is safe to deploy.
