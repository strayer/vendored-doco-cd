## Summary of Changes

This update is a modest diff (~277 insertions / 104 deletions across 19 files) that primarily **hardens the OCI signature verification trust boundary**. Two related changes tighten this boundary: in `internal/config/oci.go` (oci.go:52), a per-deployment `verify: false` can no longer downgrade a globally-enabled trust policy (new logic: `p.Enabled = p.Enabled || *override.Verify`); and a new `SelectTrustPolicyOverride` in `internal/source/oci/trust_policy.go` discards per-deployment OCI trust overrides unless the deployment config originates from a trusted source (inline `POLL_CONFIG.deployments`). Overrides shipped inside a `.doco-cd.yml` within an OCI artifact are now ignored. An internal-only `OciTrustPolicyOverrideTrusted` flag in `internal/config/deploy/deploy.go` (deploy.go:73, deploy.go:511) is set to `true` only for inline-POLL_CONFIG deployments; repository-sourced configs remain untrusted (covered by deploy_test.go:748). The new selector is wired into `internal/stages/stage_1_init.go` (stage_1_init.go:76) ahead of `VerifyWithCosign`. Net effect: a malicious OCI artifact can no longer ship a `.doco-cd.yml` that turns off its own signature verification.

The scheduler (`internal/scheduler/scheduler.go`) gains observability: container state/status capture and a `formatRunStatus` helper that parses Docker's `Exited (N) ...` string using bounded `strings.Index`/substring slicing. New Prometheus metrics (`ScheduledRunsActive`, `ScheduledRunsTotal`, `ScheduledRunDuration`, `ScheduledRunErrorsTotal`) are wired in and confirmed in `internal/prometheus/collectors.go`; manual `TriggerNow` runs now emit the same metrics as scheduled runs. A typo (`scheduledjobModeSwarm` -> `scheduledJobModeSwarm`) is renamed throughout with no semantic change.

CI and build changes are limited to a `Dockerfile` COPY-order swap (buildx plugin before the `/doco-cd` binary; pure build-cache optimization, buildx pin `0.34.1@sha256:ba49f75...` unchanged), SHA bumps for `docker/login-action` (v4.2.0) and `docker/github-builder`, a `cache-dependency-path` addition for pip, a new `docs-validation` job (`zensical build --strict`), and removal of `paths-ignore` from `test.yaml` so tests now run on doc-only PRs. All third-party actions remain SHA-pinned with version comments. No new secrets or permissions.

## Security Findings

Neither reviewer identified any security findings. Both reviewers explicitly noted the absence of backdoors, data-exfiltration patterns, new outbound channels, shell/process execution sinks, new env-var reads, or new socket/network surface. Claude Code raised one non-blocking observation: the `formatRunStatus` parser only feeds operator-visible state into a JSON `status` field returned via the existing API, with no command path involved — explicitly classified as non-blocking. The OCI trust-policy changes are characterized by both reviewers as net-positive for security, accompanied by tests pinning the intended behavior (`oci_test.go:33`, `oci_test.go:46`, `trust_policy_test.go`, `deploy_test.go:748`). Codex also noted that the scheduler's exposure of Docker container state/status through job listings increases operational visibility but does not expose secrets or grant control, and that the new Prometheus labels mirror existing scheduled-run metric labels without introducing new risk.

## Reviewer Agreement

The reviewers agreed on every substantive point: the OCI trust-policy hardening is security-positive and closes a self-attestation hole, the scheduler observability additions do not introduce risk, dependency bumps are routine with no new top-level packages, and CI changes remain SHA-pinned with no new secrets or permissions. There were no conflicts in severity or risk assessment. Claude Code's report was somewhat more granular (specific file/line citations, named Prometheus metrics, explicit safety reasoning on `formatRunStatus`), while Codex's report was more concise but reached identical conclusions.

## Verdict

**SAFE** — Both reviewers independently concluded the release introduces no security findings. The OCI trust-policy changes strictly tighten the existing trust model (preventing per-deployment downgrade of global verification and rejecting artifact-supplied trust overrides), and all other changes are observability, dependency maintenance, or build-cache optimization with no new attack surface.
