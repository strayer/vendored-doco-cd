# Security Review: doco-cd v0.111.0 -> v0.131.0

## Review Metadata

| Property | Value |
|----------|-------|
| Upgrade path | v0.111.0 -> v0.131.0 |
| Review date | 2026-10-28 |
| Reviewer 1 | Claude Code 2.1.310, model claude-fable-5-1, effort xhigh |
| Reviewer 2 | Codex codex-cli 0.164.0, model gpt-6-astra, reasoning effort xhigh |

## Summary of Changes

This upgrade spans 20 upstream releases and is the largest update this repository has vendored. Both reviewers measured the diff at 897 files with roughly 151,500 insertions and 17,300 deletions, of which Claude estimates about 60,000 lines are new non-test Go. All changes are confined to `.doco-cd-version` and `doco-cd-src/`; the enclosing repository's own GitHub workflows and build pipeline are unchanged. Upstream added a `SECURITY.md` trust model stating that repository writers, webhook secret holders, and API secret holders are all root-equivalent on the Docker host. Claude frames most findings against that model; Codex does not address it.

The codebase was substantially restructured and several subsystems were added. The Git layer replaces checkout-based clones with bare mirrors and immutable per-commit tree exports under the data mount, with in-house submodule and include resolution, packfile compaction, reference repair, a one-way startup migration of the old on-disk layout, and garbage collection (artifact GC on by default, source GC off). A self-update feature, off by default via `SELF_UPDATE_ENABLED`, lets doco-cd redeploy the Compose stack containing its own container, either by a scale-out handover or by a helper container cloned from the running one, with state kept in a journal under the data mount. The REST API was rewritten into `internal/api` and `internal/controlplane`, and an MCP server over streamable HTTP, a Swagger UI, and a loopback-only pprof server were added, all off by default. The deployment pipeline gained lifecycle hooks, recoverable one-off scheduled jobs, artifact pinning, Compose/Swarm mode migration, sync windows, pause, retry budgets, and multi-context support via the mounted Docker CLI context store.

Credential and secret handling changed in ways that affect rollout. `GIT_ACCESS_TOKEN` and GitHub App credentials are now sent only to hosts listed in `GIT_AUTH_DOMAINS`, SCM API clients refuse cross-origin redirects, and the API key check moved from plain string equality to a constant-time comparison. Secrets gained an Azure Key Vault provider, bulk fetch-by-path for all providers, OpenBao token-file re-reads and PKI chain handling, GitHub Checks reporting, two opt-in interpolation flags, and whole-artifact SOPS decryption.

On the build side, the Dockerfile now builds only `./cmd/doco-cd` plus a separate static `/healthcheck` binary with `-trimpath` instead of `./...`, Go moves to 1.27.3, and base images and the buildx plugin remain digest-pinned.

## Security Findings

### Crafted Git trees can write outside the artifact export directory

**Flagged by:** both reviewers, with conflicting severity.

**Severity:** High. Codex rated it High; Claude rated it Low to Medium and marked it unconfirmed. The consolidated rating follows Codex for the reasons given in the assessment.

**Description.** The new tree exporter in `doco-cd-src/internal/git/tree_export.go` materialises raw Git tree objects into a per-revision artifact directory. Both reviewers identified the same structural weaknesses: the symlink-target check in `exportSymlink` is lexical and does not account for intermediate symlinks, duplicate entry names in a tree are not rejected, and the real-path escape validation runs only after every file has been written (`exportTree` at line 240, `exportFile` at line 354, `exportSymlink` at line 402, final validation at line 119). Codex adds that regular files are opened with `O_CREATE|O_TRUNC|O_WRONLY`, which follows an existing symlink. Codex gives a concrete tree sequence:

```text
d/l   symlink → ..
m     symlink → d/l/../../mirror/config
m     regular file containing attacker-controlled bytes
```

For an export root of `/data/source/artifacts/.tmp-example`, lexical normalisation makes the second entry appear to stay inside the root, but real filesystem resolution follows `d/l` first and reaches `/data/source/mirror/config`. The duplicate regular-file entry then opens the existing `m` symlink and overwrites the outside file before the final validation fails. Codex confirmed from the pinned go-git v5.19.3 source (`plumbing/object/tree.go:268`) that the tree decoder appends duplicate entries rather than rejecting them; this was the precondition Claude listed as unverifiable. The exporter runs during artifact publication (`doco-cd-src/internal/source/store/git_store.go:176`) before a deployment succeeds, so rejecting the deployment afterward does not undo the write. With a writable container filesystem, Codex notes the targets include files executed later, such as the `/healthcheck` binary the image runs periodically (`doco-cd-src/Dockerfile:109`), which would yield code execution with the container's credentials and Docker socket.

**Assessment.** This is a real defect and both reviewers agree it should be fixed upstream. On severity, Codex's reasoning is more convincing: it verified the one technical gap Claude could not check, traced the write path to an executable the image runs on a schedule, and both reviewers agree the post-export validation cannot reverse the damage. Two caveats are shared: the attacker must get malformed raw objects into a source, include, or enabled submodule that doco-cd fetches, and hosting services that fsck pushes may reject duplicate-name trees. Neither reviewer executed the exploit. Claude's trust-model framing is also relevant and was not rebutted by Codex: upstream already treats write access to a fetched repository as root-equivalent, so for operator-controlled sources this is a defense-in-depth failure rather than a new trust-boundary crossing. Codex's required fix is to reject duplicate or colliding entries before materialisation, confine every write to the export root including intermediate symlink resolution, and add a regression test that verifies an outside canary file is unchanged after a failed malicious export.

### Opt-in environment interpolation can leak any process environment variable through error text

**Flagged by:** Claude only.

**Severity:** Medium (High if the flag is enabled). Default off.

**Description.** When `INTERPOLATE_EXTERNAL_SECRETS=true`, `${VAR}` in legacy secret references and secret paths is expanded with `os.LookupEnv` and no allowlist (`doco-cd-src/internal/secretprovider/types/secret_ref.go:165`, `secrets_path.go:106`). A repository writer can reference `${API_SECRET}` or `${SOPS_AGE_KEY}`. The expanded reference is echoed back in doco-cd's own error wrapping (`internal/secretprovider/openbao/client.go:252`, `resolve.go:96`), which flows into the commit status summary, Apprise failure notifications, logs, and the webhook response. For `pki-role:` references the expanded string is also written into a container label. The wiki warns only that values are sent to the provider.

**Assessment.** Real risk, but only when the flag is enabled. Codex mentioned expanded external-secret handling in its change summary without reporting a finding. Claude recommends keeping the flag off and filing an upstream issue.

### Mixed-case `FILE://` webhook clone URL bypass remains unfixed

**Flagged by:** Claude only.

**Severity:** Medium (carried over from the v0.111.0 review).

**Description.** `isWebhookGitCloneURLAllowed` at `doco-cd-src/cmd/doco-cd/handler_webhook.go:59` still relies on a case-sensitive `file://` prefix check (`internal/git/auth.go:435`). go-git lowercases the scheme, so an HMAC-authenticated webhook can select any Git directory inside the container, including other repositories' mirrors. The same release made `IsNativeGit` case-insensitive but not `IsLocalFile`. The related `SOURCE_URL_REWRITES` path-traversal note from the previous review (`handler_webhook.go:91`) is also unchanged. Claude confirmed the guard is byte-for-byte unchanged.

**Assessment.** Real but bounded: both paths require the webhook secret, which upstream's trust model treats as root-equivalent. Still open and worth tracking upstream.

### Repository content can select any mounted Docker context

**Flagged by:** Claude only.

**Severity:** Low.

**Description.** The `context` deploy key is marked `allowOverride` (`doco-cd-src/internal/config/deploy/deploy.go:74`), so a nested auto-discovered config can retarget a stack to any context in the mounted Docker CLI context store. There is no per-repository allowlist. Repository content cannot define new contexts or change endpoints or TLS settings.

**Assessment.** Only relevant to operators who mount contexts for multiple hosts. Upstream documents this as intended behavior.

### Submodule URLs are unrestricted

**Flagged by:** Claude only.

**Severity:** Low, pre-existing capability made explicit.

**Description.** `.gitmodules` URLs are used verbatim (`doco-cd-src/internal/git/tree_export.go:451-483`), so `file://` submodules can read any Git directory in the container, and `ssh://` submodules cause outbound SSH with the global key and automatic known-hosts enrollment.

**Assessment.** go-git's recursive submodule clone on v0.111.0 had the same reach, and upstream's trust model explicitly puts repository-writer reads of container files out of scope. Not a new risk, though it is one of the paths by which malicious trees could reach the exporter finding above.

### Whole-artifact SOPS decryption leaves plaintext in retained artifacts

**Flagged by:** Codex only.

**Severity:** Low.

**Description.** Decryption now covers the entire exported tree, including files no deployment uses (`doco-cd-src/internal/source/store/decrypt.go:56`). Plaintext can remain in retained artifacts, increasing the sensitive data stored under the data directory.

**Assessment.** Codex found no vulnerability here but flagged the larger sensitive footprint at rest. Claude did not comment on it; Claude's note that artifact GC keeps the two most recent revisions by default bounds how long the plaintext persists.

### Self-update creates another fully trusted process (opt-in)

**Flagged by:** both reviewers.

**Severity:** Informational. Off by default.

**Description and assessment.** Both reviewers agree the feature is disabled by default and that the applier helper is a clone of the running container's config and host config, including mounts and privileges, with ports and healthcheck removed and nothing added (`doco-cd-src/internal/docker/self_applier.go:24-61`). It is not overridable by labels or config. Codex characterises this as deliberately creating another highly trusted process. Claude adds:

- The new image comes only from the operator's own compose file in the Git repository (`internal/docker/self_update_deploy.go:432-452`, `self_apply.go:529-535`). There is no hardcoded registry or release lookup. A repository writer can therefore replace doco-cd with any image, which is no more than they could already do by deploying a socket-mounted stack.
- No signature verification of the self image exists, not even optionally.
- The journal snapshot stores the full container inspect output, including `Env`, under `<data>/self-update/` with mode 0600, removed on completion (`internal/selfupdate/journal.go:468-481, 521`). Secrets are never logged or sent to notifiers.
- `SELF_UPDATE_CRASH_AT` is an undocumented fault-injection env var compiled into production (`internal/selfupdate/crash.go:13-24`). It only causes self-termination and only an operator can set it.
- The `apply-self <id>` argument is not path-validated (`cmd/doco-cd/applyself.go:31-45`), but only a socket-privileged caller can start such a container.

### REST API, MCP server, and lifecycle hooks

**Flagged by:** both reviewers.

**Severity:** Informational.

**Description and assessment.** Both reviewers confirm that every REST handler and the MCP endpoint check `x-api-key` with a constant-time compare before any work (`doco-cd-src/internal/restapi/api.go:18-24`, `internal/mcp/handler.go:140`); Claude cross-checked all 15 handlers against the route table. MCP, Swagger UI, and pprof are off by default, and pprof binds to `127.0.0.1` only. Claude notes that MCP exposes the same control-plane functions as REST, including destroy, remove stack, trigger poll, and mirror compaction; the SDK's localhost protection is disabled, but no CORS headers are emitted and the key check precedes the transport. The API-key holder can trigger a poll against any Git or OCI URL including `file:///` with inline deploy configs (`internal/api/poll.go:51-68`), unchanged from v0.111.0. Swarm stack endpoints return raw service specs including `Env` (`internal/api/stacks.go:207, 276`), pre-existing and authenticated only. `/v1/health` and `/metrics` remain unauthenticated as before. Both reviewers agree lifecycle hooks run only inside the user's service containers via the Docker API, with Codex noting they honour the configured user and `privileged` setting; nothing executes inside the doco-cd container.

### Pre-existing privileged behaviors re-confirmed

**Flagged by:** Claude only.

**Severity:** Informational. None are new in this range.

- Scheduled jobs with `cd.doco.job.stop_services` can stop any Compose project on the host, including doco-cd itself (`doco-cd-src/internal/scheduler/scheduler_execution.go:302-342`). Present in v0.111.0.
- Swarm image pruning starts a global job from the unpinned `docker:cli` image with the socket mounted on every node (`internal/docker/swarm_job.go:87-112`). Present in v0.111.0.
- SSH host-key mismatch triggers automatic known-hosts refresh. Present in v0.111.0. This range adds `SSH_KNOWN_HOSTS_FILE`, which makes an operator-managed file authoritative and disables both enrollment and refresh. Claude recommends setting it where SSH sources are used.

### Upgrade-breaking configuration and data-layout changes

**Flagged by:** both reviewers for the credential change; Codex only for the bind-mount data-loss risk; Claude only for the migration and GC details.

**Severity:** Informational, but action is required before rollout.

- **Startup will fail** if `GIT_ACCESS_TOKEN` or GitHub App credentials are set without a matching `GIT_AUTH_DOMAINS` entry (`doco-cd-src/internal/config/app/app_config.go:384-390`). Both reviewers flag this. Claude's example is `GIT_AUTH_DOMAINS: "- domains: [github.com]"`. Both reviewers advise against the `GIT_AUTH_ALLOW_ANY_HOST=true` escape hatch, which disables the new protection.
- **Relative bind mounts can lose application data.** Codex reports that a mount such as `./data:/var/lib/postgresql/data` now refers to revision-specific storage; deployments can move to a fresh directory, and legacy checkout cleanup or artifact GC can later remove the old data (`internal/migration/migration.go:760`, `wiki/docs/Reference/Artifact-Storage.md:12`). Upstream documents this. Codex's instruction is to back up and migrate such mounts to named volumes or stable absolute paths outside artifact storage before upgrading.
- **The layout migration is one-way** and runs automatically at startup. Claude reports it walks the whole data mount, renames `.git` to `mirror`, and removes remaining working-tree files for repositories no running container references by label (`migration.go:311-372, 784`). All paths are confined to the data mount, symlinks are skipped, and Docker resources are only listed. Rolling back to v0.111.0 would require re-cloning.
- **Artifact GC is on by default** and removes unreferenced `artifacts/<sha>` directories beyond the two most recent after one minute. Store detection is structural, so unrelated directories placed under `/data` with an `artifacts/` or `mirror/` child could be swept.
- **Healthcheck** moved to a separate `/healthcheck` binary. The old `doco-cd healthcheck` subcommand still works but is deprecated.

### Verified negatives

**Flagged by:** both reviewers.

**Severity:** Informational.

Both reviewers found no evidence of a deliberate backdoor, hidden network destination, or data-exfiltration mechanism, and no suspicious build-time execution. Claude's specific checks:

- No `os/exec` in any production package. The only occurrences are the e2e harness, a dev-time schema generator, a pre-existing `exec.LookPath` for credential-helper diagnostics, and `internal/test/git_daemon.go`. That test package is linked into the binary through one helper call in `internal/reconciliation/deploy.go:239`, but its exec paths require a `*testing.T` and are unreachable at runtime.
- No shelling out to `docker` or `docker compose` binaries; Compose runs in-process.
- No hardcoded IPs or encoded blobs. All hardcoded URLs are provider defaults, SCM APIs, Docker Hub, and the pre-existing GitHub release check, now gated by `VERSION_CHECK_ENABLED`.
- No `InsecureSkipVerify` outside the localhost healthcheck probe. Cosign OCI verification is not weakened and cannot be disabled by repository content.
- Credentials are per-host and never inherited from a parent repository to its submodules. Wildcard domain entries never match the apex or lookalike suffixes.
- No secrets in container labels, Prometheus labels, or scheduler state files. Secret provider endpoints come from the environment only.
- Workflow files under `doco-cd-src/.github/` are SHA-pinned and never run in this repository. Wiki build hooks invoke only the project's own Go generators.

## Reviewer Agreement

The reviewers agreed on the absence of malicious code, backdoors, or exfiltration paths; on the cleanliness of the dependency changes; on the defaults-off posture of MCP, self-update, Swagger, and pprof; on the hardening value of host-scoped Git credentials, redirect restrictions, and constant-time API key comparison; on the `GIT_AUTH_DOMAINS` startup break; and on the existence of the tree-export defect. They differed sharply on that defect's severity and on the resulting verdict: Claude rated it Low to Medium and unconfirmed and concluded SAFE WITH NOTES, while Codex verified the go-git decoder behavior, rated it High, and recommended blocking deployment until it is fixed. Coverage also differed. Claude alone reported the interpolation leak, the carried-over `FILE://` bypass, Docker context selection, unrestricted submodule URLs, and the pre-existing privileged behaviors, and alone had the comparison against v0.111.0 to classify what is new. Codex alone reported SOPS plaintext retention and the relative bind-mount data-loss risk, and alone had access to dependency source.

## Verdict

**SAFE WITH NOTES.** Neither reviewer found malicious code, a backdoor, or an exfiltration path, and the release is net hardening; the one High finding, the tree-export write escape, is an upstream defect whose prerequisite, write access to a Git source doco-cd fetches, is already root-equivalent under upstream's stated trust model, and it further depends on the Git host accepting malformed trees, with no exploit executed by either reviewer. It must be reported upstream with Codex's proposed fix, and deployments that fetch from hosts that do not reject malformed objects, from `file://` sources, or from third-party submodules should treat it as blocking until a fix ships. Before rollout, set `GIT_AUTH_DOMAINS`, migrate any relative bind mounts holding persistent data, keep `INTERPOLATE_EXTERNAL_SECRETS` off, and consider `SSH_KNOWN_HOSTS_FILE`.
