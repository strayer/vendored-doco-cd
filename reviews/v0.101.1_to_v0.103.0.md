## Summary of Changes

The update spans upstream releases v0.102.x and v0.103.0, touching 45 files (+1,764 / −196), the majority being tests and documentation. The headline feature is support for SSH-based Docker contexts: the previously pure-distroless runtime image now bundles an OpenSSH client, installed from a digest-pinned `debian:trixie-slim` stage with only the `ssh` binary and missing shared libraries copied into the digest-pinned distroless base (`doco-cd-src/Dockerfile`). This enables deploying stacks to remote Docker daemons over `ssh://` contexts.

Several new operator-facing configuration knobs are introduced: `GIT_ACCESS_TOKEN_USER` (plus per-domain `git_access_token_user`) sets the HTTP Basic-Auth username for git token auth (defaulting to `oauth2`, primarily for GitLab deploy tokens, replacing the unused `AUTH_TYPE` variable); `GIT_SCM_API_URL` optionally overrides the SCM API base URL used for commit-status calls, validated to be `http(s)://` with query/fragment stripped; and `APPRISE_NOTIFY_BODY_TEMPLATE` allows a custom Go `text/template` notification body, validated at startup with render failures falling back to the built-in body. Notification metadata also gains a `Context` field identifying the target Docker context.

Robustness fixes include: commit-status POSTs now retry up to 4 times with backoff on network errors, 408/429, and 5xx; SSH clone URLs with custom ports have the port stripped when deriving the HTTPS API host; Docker CLI context-initialization errors are captured and surfaced instead of silently ignored; Compose stacks with `enable_ipv6` but no explicit IPAM subnet are force-recreated to avoid a parser failure; and reconciliation gains panic recovery around job goroutines plus permanent-error handling (e.g. a missing `ssh` binary) in the Docker event listener. CI changes are limited to SHA-pinned action bumps in upstream's own (inert, vendored) workflows; the vendor repository's build/sync workflows are unchanged.

Both reviewers independently verified vendoring integrity: Claude Code diffed the vendored tree against the upstream v0.103.0 release tarball (byte-identical), and Codex compared all 380 tracked blobs including modes and Git object hashes against the live upstream tag (exact match). The only absences are a handful of `.env` test fixtures (and `test-cases/`, per Claude Code) excluded by this repo's pre-existing sync process — the same exclusions already present on `main`. No executable-bit changes, submodules, symlinks, or binary blobs were introduced.

## Dependency Review

**No new Go dependencies.** Both reviewers confirmed `go.mod` contains only patch-level bumps of established modules: `go-billy` 5.9.0→5.9.1, `moby/client` 0.5.0→0.5.1, `prometheus/client_golang` 1.24.0→1.24.1, `klauspost/compress` 1.19.0→1.19.1, and `go.yaml.in/yaml/v3` 3.0.4→3.0.5, with `go.sum` matching. The `retry-go/v5` import newly used in the commit-status package was already a project dependency. Neither reviewer found anything resembling an obscure tunneling, execution, or cryptography package.

There is one new **OS-level** dependency: `openssh-client` in the runtime image. Codex noted that while both base images are digest-pinned, `apt-get install openssh-client` does not pin a package version, so rebuilding the same commit later could yield a different SSH binary. This is a reproducibility gap rather than anything suspicious; Codex recommends recording/scanning the resolved package version or using a Debian snapshot/package lock.

## Security Findings

### 1. SSH contexts allow repository authors to deploy across trust zones

Codex flagged that repository-controlled deployment configuration already selects a Docker context by name (`doco-cd-src/internal/config/deploy/deploy.go:52`). With SSH contexts now operational, a single doco-cd instance provisioned with SSH contexts for multiple trust zones would let a repository author target any pre-provisioned context and deploy arbitrary containers there — and Docker access typically implies root-equivalent control of the remote host. Important limits apply: a repository cannot invent an arbitrary SSH endpoint (the context must already exist in the mounted Docker configuration), nothing changes for local/default-context deployments, and the same boundary already existed for TCP contexts — this release merely makes it operational for SSH.

- **Flagged by:** Codex only. Claude Code did not address the repository-to-context trust boundary; there is no conflict, just differing coverage.
- **Severity:** High — conditional, applying only when SSH contexts spanning trust zones are provisioned to one instance. Not applicable for local/default-context deployments.
- **Assessment:** Real risk if and only if the deployment topology enables it. Codex's mitigation is sound: run separate doco-cd instances per trust zone or enforce an external repository-to-context policy, and never expose production context credentials to an instance processing less-trusted repositories.

### 2. Documentation recommends insecure SSH credential handling

Both reviewers flagged that the new Docker-contexts documentation suggests `StrictHostKeyChecking no`, which disables authentication of the remote Docker host and weakens MITM protection. Codex additionally identified that the docs recommend mounting the host's entire `~/.docker` and `~/.ssh` directories, and running `chmod -R a+r ~/.docker/contexts/`, which can make context TLS private keys world-readable on a multi-user host (`doco-cd-src/wiki/docs/Advanced/Docker-Contexts.md`). Per Codex, a fake SSH endpoint accepted without host verification could observe Docker API requests, deployment configuration, registry credentials, or uploaded secrets.

- **Flagged by:** Both. Claude Code treated it as an informational documentation-only note; Codex rated it Medium and enumerated more problematic guidance in the same document.
- **Severity:** Medium. Codex's position is more convincing: while nothing is applied automatically, documentation of this kind is routinely copy-pasted into privileged production deployments, and Codex identified two additional hazards (broad credential mounts, world-readable key permissions) beyond the host-key issue Claude Code noted.
- **Assessment:** Not a code vulnerability, but a real operational risk for anyone adopting SSH contexts by following the docs verbatim. Both reviewers converge on the mitigation: pinned `known_hosts` (or at minimum `accept-new`), a dedicated SSH key restricted to Docker transport, narrow mounts containing only the required material, and restrictive permissions.

### 3. `GIT_SCM_API_URL` redirects the Git access token to an operator-chosen endpoint

When set, this new option replaces the repository-derived API destination for commit-status calls, and those requests carry the full Git token in the `Authorization` header (`doco-cd-src/internal/commitstatus/commitstatus.go`, `http_client.go`). Both reviewers verified it is exclusively operator-controlled environment configuration — never derived from repository content or webhooks — scheme-validated, and disabled by default.

- **Flagged by:** Both, with matching assessments.
- **Severity:** Low.
- **Assessment:** Not a vulnerability or backdoor; it is a new credential-bearing egress knob that is only as dangerous as the rest of the environment configuration. Treat it as sensitive: use HTTPS only, verify the override hostname belongs to the intended SCM provider, and prefer a domain-scoped, least-privileged status token.

### 4. OpenSSH client expands the attack surface of a formerly distroless image

Claude Code noted that the release image now ships a fully capable `/usr/bin/ssh`. For a container that holds the Docker socket and git/registry credentials, this adds a living-off-the-land binary an attacker could use for outbound tunnels — but only if they first achieved code execution by other means. All sources are digest-pinned and the binary exists to support the documented feature.

- **Flagged by:** Claude Code (Codex discussed the SSH addition primarily through the trust-boundary lens of finding 1).
- **Severity:** Informational.
- **Assessment:** Not a vulnerability by itself. Deployments that never use SSH Docker contexts can strip the `COPY` of the ssh binary in their own build to keep the image minimal, as Claude Code suggests.

## Reviewer Agreement

The reviewers agreed on all load-bearing conclusions: the vendored tree exactly matches upstream v0.103.0 (verified by two independent methods, with the same benign pre-existing fixture exclusions — Codex counted three absent `.env` fixtures, Claude Code four items including `test-cases/`, which is consistent rather than contradictory), no new Go dependencies were introduced, the notification templates are inert (no function map, filesystem, environment, or command access), the retry logic is bounded and does not leak tokens, and `GIT_SCM_API_URL` is a low-risk operator-controlled knob. They differed mainly in emphasis on the SSH feature: Claude Code framed it as an attack-surface note and issued an unconditional "safe to deploy" verdict, while Codex identified the repository-controlled context-selection trust boundary and made its approval conditional on trust-zone separation for SSH/multi-host contexts — a distinction of coverage and framing rather than a factual disagreement.

## Verdict

**SAFE WITH NOTES.** The diff is a byte-verified faithful copy of upstream v0.103.0 with no backdoors, exfiltration paths, or suspicious dependencies, and is safe to build and deploy as-is with the existing local/default Docker context. If SSH or multi-host Docker contexts are adopted, apply Codex's conditions — per-trust-zone instance separation, strict host-key verification, dedicated narrowly-mounted credentials — and do not follow the vendored documentation's `StrictHostKeyChecking no` / broad-mount examples.
