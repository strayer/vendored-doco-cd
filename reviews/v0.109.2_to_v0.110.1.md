## Summary of Changes

This update covers upstream releases v0.110.0 and v0.110.1: two commits (a version bump and an `[Auto] Sync source code` commit), 82 changed files, roughly 5,056 insertions and 245 deletions, all confined to `.doco-cd-version` and the vendored `doco-cd-src/` tree. Both reviewers confirmed no repo-local tooling or CI configuration outside the vendored tree was touched, and Reviewer 2 verified the merge-base equals `origin/main` with a clean worktree throughout.

The largest feature additions are TLS and certificate handling. New env vars `HTTP_TLS_CERT_FILE` / `HTTP_TLS_KEY_FILE` enable optional HTTPS on the webhook/API server and the Prometheus metrics server, with startup validation requiring both to be set together. A new OpenBao `pki-role:` secret reference type can mint fresh certificate/key pairs via the PKI engine's `issue/<role>` endpoint, delivering the private key as `<NAME>_KEY` through the existing in-memory external-secrets path. On top of that, an opt-in certificate-rotation watcher (disabled by default, OpenBao provider only) monitors deployments labeled as carrying rotatable certificates, checks expiry and revocation (via `<engine>/certs/revoked`), reissues certificates, and redeploys the affected Compose services or Swarm stacks. Docker labels store only certificate references, serials, and expiry metadata — never key material.

Two smaller behavioral changes: Docker registry credentials are now re-read from `config.json` on every auth lookup so rotated short-lived tokens (ECR/GCR/ACR) work without a restart, and repeated failure notifications are fingerprinted (SHA-256, in-memory) and suppressed for `APPRISE_NOTIFY_REPEAT_INTERVAL` (default one hour).

Fixes include: GitHub App installation tokens now also back commit-status API calls (explicit access tokens still take precedence), the scheduler preserves `lastRun` across job-definition edits, deploy-start readiness requires three consecutive ready samples and treats `restarting` as a crash, image-digest drift is reported per service, and project hashes are normalized so freshly reissued certificates don't trigger spurious redeploys.

## Dependency Review

Both reviewers independently confirmed **zero new direct Go dependencies**. Existing dependencies received patch/minor bumps: Docker Compose 5.4.0 → 5.5.0, BuildKit 0.32.1 → 0.32.2, buildx 0.36.0 → 0.36.1, AWS SDK v2 patches, gRPC 1.82.1 → 1.83.0, and `golang.org/x/{mod,net,tools,telemetry}` updates. `go.sum` gains one new module path, `github.com/moby/sys/mount v0.3.5` — an official Moby ecosystem package pulled in transitively by the Docker/Compose updates; both reviewers assessed it as not suspicious.

Build inputs are likewise clean: the golang base image stays at 1.26.6 (digest refresh only), GitHub Actions changes are pin-hash updates of already-used actions without expanded workflow permissions, and the docs generator `zensical` moves from 0.0.53 to 0.0.56 (documentation tooling only, not part of the runtime image).

## Security Findings

Neither reviewer found backdoors, exfiltration mechanisms, new network destinations, new shell/process execution, or obfuscated code. The findings below are hardening notes and one reliability defect.

### OpenBao PKI issuance and cert-rotation watcher expand what the secret provider can do

The new `pki-role:` references let repository deployment configuration select the PKI mount, role, namespace, and common name for certificate issuance, and the rotation watcher lets a revoked or expiring certificate trigger autonomous redeploys of labeled stacks.

- **Flagged by:** Both reviewers, with a difference in emphasis. Reviewer 2 called this "a real capability expansion" warranting explicit deployment conditions: restrict the doco-cd OpenBao token to approved PKI mounts and roles, constrain permitted common names/domains per role, avoid broad `pki/*` write policies, and treat repositories allowed to define `external_secrets` as trusted inputs. Reviewer 1 assessed that it "does not materially expand the trust placed in" the secret provider, since that provider already fully controls all secret values injected into deployments, and noted redeploy metadata lives in Docker labels only a root-equivalent actor could forge.
- **Severity:** Informational
- **Assessment:** Both positions are compatible: this is not a code-level vulnerability (the OpenBao policy remains the authorization boundary, and issued private keys traverse only the pre-existing in-memory secrets path), but new API capability is genuinely reachable from repository config. Reviewer 2's framing is the more actionable one for a privileged deployment — the feature is safe as shipped, but the OpenBao token policy should be scoped to the specific PKI mounts and roles actually needed before the feature is used. Rotation is off by default; note that `pki-role:` issuance itself occurs whenever such a reference is used, independent of the watcher.

### Potential panic on scp-style git remotes in the resource loader

`internal/docker/git_resource_loader.go` adds `strings.Split(ref.Remote, "/")` followed by `strings.Join(r[3:], "/")` for a debug log line. An scp-style compose include remote (e.g. `git@host:org/repo.git`) yields fewer than four segments and would panic with a slice-bounds error, potentially crashing a poll job.

- **Flagged by:** Reviewer 1 only.
- **Severity:** Low
- **Assessment:** A real defect, but availability-only, and only triggerable by someone who can already author deployed compose files — no trust-boundary violation. Worth reporting upstream; not a blocker.

### Failure-notification deduplication may suppress repeated security-relevant alerts

Repeated failure notifications are now suppressed for one hour by default via `APPRISE_NOTIFY_REPEAT_INTERVAL`.

- **Flagged by:** Reviewer 2 (Reviewer 1 described the mechanism without raising a concern).
- **Severity:** Informational
- **Assessment:** An operational monitoring consideration, not a vulnerability. Operators whose security monitoring depends on receiving every repeated failure event should set `APPRISE_NOTIFY_REPEAT_INTERVAL=0`.

### `InsecureSkipVerify` in the container healthcheck

The container healthcheck switches to `https://localhost:...` and disables TLS verification to accommodate self-signed certificates.

- **Flagged by:** Both reviewers, both assessing it as acceptable.
- **Severity:** Informational
- **Assessment:** Not a risk. The bypass is scoped to a container-local localhost self-check and does not apply to general outbound traffic; both reviewers agree it is the correct trade-off.

### Upstream source provenance not cryptographically verified

- **Flagged by:** Reviewer 1, as an explicit limitation: network egress was not approved in its sandbox, so the vendored tree could not be byte-compared against the upstream v0.110.1 tag. Reviewer 2 did not perform this check either (its validation was limited to diff hygiene and static review; no build or tests were run to preserve read-only mode).
- **Severity:** Informational
- **Assessment:** Not a finding against the diff itself — the sync commit follows the repo's established pattern and nothing contradicts the upstream changelog scope. Reviewer 1's suggestion stands as hardening advice: if the sync pipeline doesn't already verify the upstream tag hash, adding that would close this gap for future reviews.

## Reviewer Agreement

The reviewers agreed on essentially everything material: scope of the diff, a clean dependency picture, no malicious patterns or exfiltration channels, key material never landing in labels or logs, the localhost-only scope of `InsecureSkipVerify`, and an overall safe verdict. Their only divergences were in coverage and emphasis: Reviewer 1 uniquely identified the potential panic on scp-style git remotes and the unverified upstream provenance, while Reviewer 2 uniquely raised the notification-suppression monitoring note and framed the OpenBao PKI additions as a capability expansion requiring least-privilege policy — a stronger framing than Reviewer 1's "no material trust expansion," and the more prudent one for a privileged deployment, though the two assessments do not actually contradict each other.

## Verdict

**SAFE WITH NOTES** — Both reviewers independently found no malicious code, no exfiltration, no new dependencies of concern, and no unexpected privilege expansion, so the image is safe to build and deploy. The notes: scope the OpenBao token to specific PKI mounts/roles before using the new `pki-role:` feature, consider `APPRISE_NOTIFY_REPEAT_INTERVAL=0` if monitoring requires every failure event, and report the low-severity scp-style-remote panic upstream.
