## Summary of Changes

The diff spans 104 files with roughly 5,300 insertions and 830 deletions. Reviewer 1 additionally verified that the vendored source is byte-identical to the upstream `v0.101.1` git tag (the only differences being upstream test-data files the sync script intentionally excludes), so no code was injected during vendoring; the only change outside `doco-cd-src/` is the `.doco-cd-version` bump. Reviewer 2 confirmed there were no executable-bit, symlink, submodule, or suspicious binary changes.

Two genuinely new capabilities dominate the release. First, an optional commit-status reporting feature (new `internal/commitstatus` package, ~1,300 lines including tests) posts deployment outcomes to GitHub/GHES, GitLab, Gitea/Forgejo/Gogs, and Azure DevOps — the one new outbound network path, disabled by default via `GIT_COMMIT_STATUS=false`. Second, per-deployment Docker-context support lets deploy configs target multiple Docker daemons (including remote hosts) via a repository-configurable `context:` field, with reconciliation, cleanup, and deployment routed through the selected context.

The release also contains substantial security hardening: OCI artifacts are now digest-pinned and Cosign-verified *before* extraction or reconciliation cleanup, with bounded extraction (1 GiB / 100k entries), temp-dir staging, and layout validation; empty REST API keys now fail closed (previously an empty configured key allowed all requests — a real vulnerability fixed); GitLab webhook tokens are compared in constant time; the HTTP server gained read/idle timeouts (Slowloris mitigation); the Bitwarden SDK state file moved from world-readable `/tmp` to a 0700 per-user directory; SOPS directory decryption gained symlink-loop protection; and fire-and-forget goroutines gained panic recovery.

Remaining changes are routine: scheduler improvements (`SCHEDULER_ENABLED`, swarm scheduled-job services pinned to 0 replicas), domain-scoped Git authentication and GitHub App credentials, dependency and toolchain bumps, base-image digest updates, SHA-pinned CI action bumps, tests, and documentation. Both reviewers independently confirmed that the documented "self-updating" feature is purely a two-instance deployment pattern described in the wiki — there is no auto-update or remote-code-download code in the binary.

## Dependency Review

No new direct dependencies were added. The only completely new module identity is the indirect dependency `github.com/clipperhouse/uax29/v2 v2.2.0`, a legitimate and widely used Unicode text-segmentation library pulled in by the docker/cli stack as a replacement for `rivo/uniseg`. All other changes are version bumps of existing dependencies (Docker CLI/Compose, Moby, SOPS, Cosign 3.1.1→3.1.2, AWS SDK, OpenBao, Prometheus, BuildKit, OpenTelemetry, gRPC, golang.org/x), Go 1.26.4→1.26.5, and Buildx/distroless digest updates. Both reviewers agree nothing in the dependency diff resembles an obscure execution, tunneling, cryptography, or exfiltration package, and CI actions remain pinned to full commit SHAs with no permission expansion.

## Security Findings

### Repository-selectable Docker contexts widen the blast radius across trust zones

The new `context:` field in repository deploy configs is passed directly into Docker CLI context selection, and there is no allowlist binding a repository to its permitted contexts. Both reviewers flagged this, with different emphasis. Reviewer 2 rated it **High, configuration-dependent**: if one doco-cd instance is given contexts spanning hosts of unequal trust (per the documented pattern of mounting the host's entire `~/.docker` including context credentials), any repository with push access to its own `.doco-cd.yml` can select a production context and deploy an attacker-controlled privileged container on that daemon — effectively host-root access on that machine. Reviewer 1 treated it as an observation rather than a blocking finding, emphasizing that arbitrary hosts cannot be named — only contexts the operator explicitly pre-provisioned (`CreateDockerCliWithContext` fails for unknown names) — and that behavior is unchanged if no extra contexts are created.

- **Flagged by:** Both reviewers; conflicting severity assessments.
- **Severity:** High (configuration-dependent); Informational for default single-daemon deployments.
- **Assessment:** The two reports agree on the facts and disagree only on framing; Reviewer 2's severity rating is the more convincing for anyone who mounts multiple contexts, because the absence of any repository-to-context binding means the security boundary rests entirely on deployment architecture rather than on code. Reviewer 1's point stands for the default path: with no extra contexts mounted, nothing changes. The practical policy is Reviewer 2's recommendation — run separate doco-cd instances per trust zone, expose each only to the contexts its repositories may manage, and do not mount production context credentials into an instance processing less-trusted repositories.

### Commit-status reporting: authenticated outbound egress with two caveats

When `GIT_COMMIT_STATUS` is enabled (it is off by default), doco-cd makes authenticated GET/POST requests to the repository provider's API, with a 15-second client timeout and provider error bodies capped at 4 KiB. Both reviewers judged this intentional functionality, not covert exfiltration, and each noted a distinct caveat. Reviewer 1: the target host prefers `payload.WebURL` from the webhook payload; payloads are HMAC-authenticated, but if the feature is enabled *and* the webhook secret were compromised, a forged payload could direct the git token to an attacker-controlled host. Reviewer 2: the raw deployment error text (whitespace-normalized, truncated to 140 characters) is used as the failure description, and such errors can leak paths, internal hostnames, or sensitive provider messages into commit statuses.

- **Flagged by:** Both reviewers, with complementary caveats.
- **Severity:** Low.
- **Assessment:** Real but minor residual risk, and entirely irrelevant while the feature remains disabled. If enabled, use least-privileged, domain-scoped tokens, protect the webhook secret, and consider who can see repository statuses. The token otherwise flows only to the host parsed from the repository's own URL (or `api.github.com`) — no hardcoded third-party endpoints exist.

### New `ignore_tlog` OCI trust-policy option weakens Cosign verification when set

A new trust-policy option skips transparency-log verification. Both reviewers noted it defaults to false and is only honored from the operator's global policy or from overrides gated by the pre-existing `OciTrustPolicyOverrideTrusted` flag (operator-supplied `POLL_CONFIG` only); repository-controlled configs cannot set it for untrusted sources, and deployment-level `verify: false` still cannot disable global verification.

- **Flagged by:** Both reviewers, in agreement.
- **Severity:** Informational.
- **Assessment:** Not a risk as shipped — it is operator-gated and off by default. Worth knowing about only if an operator later chooses to enable it.

## Reviewer Agreement

The reviewers agree on all essential conclusions: no backdoors, no covert exfiltration, no malicious or suspicious dependencies, the "self-updating" feature is documentation only, the release is net security-positive, and it is safe to build and safe to deploy on the existing single/default Docker daemon. They also identified the same two notable features and the same sole new (indirect) dependency. They differ mainly in framing the Docker-context feature: Reviewer 1 treated it as a non-blocking design observation, while Reviewer 2 rated it a High configuration-dependent risk and conditioned approval on not spanning trust zones with one instance — a difference of severity, not of fact. Additionally, only Reviewer 1 verified the vendored source byte-for-byte against the upstream tag, and each reviewer surfaced a distinct caveat on the commit-status feature.

## Verdict

**SAFE WITH NOTES** — Both reviewers found no malicious code, no suspicious dependencies, and a net security improvement, and both approve building and deploying against the current single/default Docker daemon. The notes: do not use the new multi-context feature to span trust zones from one instance (there is no repository-to-context allowlist), and if commit-status reporting is ever enabled, use least-privileged tokens and protect the webhook secret.
