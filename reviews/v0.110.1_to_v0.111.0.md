| Property | Value |

## Summary of Changes

This release's dominant feature is support for **local filesystem Git repositories as deployment sources**. Poll jobs can now use `file:///path` URLs (or absolute paths, which are normalized to `file://`) to deploy from Git repositories bind-mounted into the container — intended for chicken-and-egg scenarios such as deploying one's own Forgejo/Gitea instance. The implementation registers a pure-Go, in-process `file://` transport for go-git (`internal/git/local_transport.go`) that notably **replaces go-git's default file transport, which shells out to the `git-upload-pack` binary** — removing a subprocess-execution path rather than adding one. It supports normal, bare, worktree, and submodule-style Git directories; all file reads go through go-billy chroots, with small metadata files read via a 4 KB `LimitReader`.

A companion fsnotify-based watcher (`internal/git/local_watcher.go`) monitors the repo's `refs/heads/` and `packed-refs` to trigger polls immediately on new commits, controlled by a new `watch: true` poll-config option. It is strictly read-only with debouncing. The poll loop in `handler_poll.go` was reworked to integrate the watcher, including a 24 h safety-net interval so `interval: 0` jobs cannot busy-loop or go silent.

On the hardening side, `handler_webhook.go` gains `isWebhookGitCloneURLAllowed`, which rejects `file://` clone URLs supplied directly in webhook payloads with HTTP 403 — local URLs are meant to be reachable only via operator-configured `SOURCE_URL_REWRITES` rules. Both reviewers examined this guard closely; each identified a distinct weakness in it (see findings below). Additionally, the `joho/godotenv` dotenv parser is replaced with the already-vendored `compose-spec/compose-go/v2/dotenv`, enabling `${VAR}` interpolation across previously loaded env files; parsing stays in-process, and the lookup callback reads only the deployment's accumulated environment map, not the doco-cd process environment.

Housekeeping changes include pinned-SHA bumps of the distroless base-image digest and two GitHub Actions (the new CodeQL SHA is the official v4.37.8 release commit), a Makefile default-build change to the CGO-free `nobitwarden` target (Docker image behavior unchanged), and test/documentation updates. The workflows live under `doco-cd-src/.github/` and never execute in this vendoring repository. Both reviewers confirmed the diff matches the official v0.111.0 release description.

## Dependency Review

No new dependencies were introduced. `github.com/fsnotify/fsnotify v1.10.1` — the canonical, widely-used Go filesystem-notification library — is promoted from indirect to direct dependency; its exact version and checksums were already present in the previous `go.sum`, so no previously unseen code enters the tree. `github.com/joho/godotenv` is removed, and the `zensical` documentation tool moves from 0.0.56 to 0.0.57. Neither reviewer found any new network, cryptographic, process-execution, plugin-loading, or obscure system-access libraries; `go.sum` shrank overall. CI actions and the base image remain immutable-SHA/digest pinned.

## Security Findings

### Alternate `file:` URL syntax bypasses the webhook local-URL restriction

**Flagged by:** Reviewer 2 (Codex) only.

**Severity:** Medium

The new webhook safeguard only treats a URL as local when it begins exactly with lowercase `file://` (`strings.HasPrefix` in `internal/git/auth.go:357`). Syntactically equivalent forms such as `file:/absolute/repo` or mixed-case `FILE:///absolute/repo` are not canonicalized by `NormalizeGitURL`, and the project's URL validator accepts `file:/absolute/repo` because it only requires a `file` scheme, an empty host, and an absolute path. go-git parses these through `net/url` and routes them to the globally registered local transport, which can open any Git repository path readable inside the container. A correctly authenticated webhook sender could therefore directly select a readable local Git repository without any operator-configured rewrite — contrary to the documented security boundary.

**Assessment:** Real, but bounded. As Codex notes, this is not an unauthenticated compromise: webhook signatures are verified before payload parsing, and a valid webhook signer can already point doco-cd at an arbitrary *remote* repository capable of supplying privileged deployment configuration — so the marginal capability gained is local-filesystem reads rather than new RCE. It is a genuine defect in a control the release explicitly advertises, and it should be fixed upstream before the webhook guard is relied upon. Reviewer 1 did not identify this variant; Codex's reasoning is specific and well-evidenced (exact code locations and go-git's parsing behavior), so the finding stands as the more significant of the two guard weaknesses.

### Path traversal through `SOURCE_URL_REWRITES` prefix substitution

**Flagged by:** Reviewer 1 (Claude Code) only.

**Severity:** Low

`rewriteSourceURL` performs plain prefix substitution without path cleaning, and `NormalizeGitURL` does not clean strings that already contain `://`. An HMAC-authenticated webhook payload carrying a crafted clone URL (e.g. `https://forgejo.example.com/../../other/repo.git`) that matches a rewrite rule targeting a local path could escape the intended prefix (e.g. `/local-repos/`) via `..` and reach a different container-visible path.

**Assessment:** Real but very narrow. Exploitation requires the webhook secret (or control of the configured SCM, where `..` is not a valid repository name), an operator who has configured a local-path rewrite rule, *and* attacker-controlled Git content at another container-visible path. Worth an upstream issue; not a deployment risk for a setup using no local-path rewrites. This finding and the previous one are related — both are incomplete-canonicalization gaps around the same local-URL boundary — and would sensibly be fixed together upstream with proper URL canonicalization and path cleaning.

### New capability: local filesystem repository access (by design, operator-gated)

**Flagged by:** Both reviewers, as an observation rather than a defect.

**Severity:** Informational

The `file://` transport chroots from `/`, so any path visible inside the container can serve as a deploy source. Both reviewers agree this is the feature's intended purpose and that the legitimate entry points — `POLL_CONFIG` and `SOURCE_URL_REWRITES` — are operator-controlled environment configuration. The feature is inert unless the operator mounts repository paths into the container and opts in. Codex adds two operational recommendations: any such mount should be dedicated and read-only, and anyone able to modify a watched repository effectively controls privileged deployment input. The watcher adds filesystem handles and immediate deployment triggers but grants no filesystem access beyond what the container already possesses.

Beyond these items, neither reviewer found backdoors, exfiltration paths, encoded blobs, unexpected network destinations, new command execution, new Docker API permissions, or authentication bypasses. The only URLs added in the diff are `example.com` test fixtures and documentation links, and clone destinations still pass through the existing `/data` path-containment checks.

## Reviewer Agreement

The reviewers agree on the overall picture: the diff matches the advertised release scope, no malicious code or suspicious dependencies are present, the new local-repository feature is operator-gated and net security-positive (it removes a subprocess-based transport and a dependency), and the update is safe to build and deploy. They diverge only in which weakness of the new webhook local-URL guard they surfaced: Codex found an alternate-syntax bypass of the guard itself (Medium), while Claude Code found a path-traversal escape through rewrite rules (Low). The findings are complementary rather than conflicting — together they show the guard is not yet robust enough to be treated as a hard security boundary. Neither reviewer could fully cross-verify externally: Claude Code's sandbox blocked network access to upstream, and Codex ran no build or tests due to read-only constraints.

## Verdict

**SAFE WITH NOTES** — Both reviewers independently found no malicious code, no new dependencies, and a net security-positive change set, and both cleared the release for deployment. The notes: the new webhook guard against local `file:` URLs has two authenticated-attacker bypasses (alternate URL syntax; path traversal via rewrite rules) that should be reported upstream and fixed before webhook-triggered local mirrors or local-path rewrites are enabled or relied upon; deployments not using local repository sources are unaffected.
