## Summary of Changes

This is a small, focused upstream release spanning 15 files (+644/−88 lines), delivered via the established automated vendor-sync workflow (sync commit authored by `github-actions[bot]`, consistent with prior updates). Both reviewers confirmed the diff `origin/main...HEAD` represents the complete change set, consisting of the `.doco-cd-version` bump and the automated source synchronization.

The main functional change is a new trusted-proxy client-IP resolution feature (`cmd/doco-cd/request_ip.go`, ~200 lines). It resolves the "real" client IP from `X-Forwarded-For`, RFC 7239 `Forwarded`, or a custom header, gated by two new environment variables: `TRUSTED_PROXY_NETWORKS` (default: loopback, all RFC 1918 private ranges, and `::1`) and `TRUSTED_PROXY_HEADER` (default: `X-Forwarded-For`). All API and webhook handlers now log the resolved IP instead of the raw `r.RemoteAddr`. The implementation handles IPv4, IPv6, and IPv4-mapped IPv6 normalization, and forwarded headers are only honored when the direct TCP peer is inside the trusted networks.

The second functional change fixes an upstream regression (issue #1674): `scheduler.TriggerNow` gains a `secretProvider` parameter so scheduled jobs triggered via the REST API resolve `external_secrets` correctly, restoring parity with cron-triggered runs. A regression test covers this.

The remainder is build and CI housekeeping: `--no-install-recommends` on apt, removal of redundant bind mounts, relocation of the `APP_VERSION` ARG for better layer caching, per-branch CI concurrency groups, scoped GitHub Actions cache scopes, and removal of an unnecessary QEMU setup step from upstream's amd64-only development build. Documentation and tests accompany the new features. The seemingly large `app_config.go` diff is roughly 95% whitespace realignment of struct-tag comments; only the two new config fields are substantive.

## Security Findings

### Permissive default `TRUSTED_PROXY_NETWORKS` allows logged-IP spoofing from private networks

**Description:** The default trusted-proxy list covers loopback plus all common RFC 1918 private IPv4 ranges and `::1`, rather than specific proxy addresses. Any direct peer whose source address falls within those ranges (e.g., any workload on the same private or Docker network) can supply a forged `X-Forwarded-For` header and influence the client IP recorded in logs.

**Flagged by:** Both reviewers. Reviewer 1 characterized it as a "minor residual caveat (informational, not a defect)"; Reviewer 2 framed it as a "non-blocking audit-log integrity concern." The difference is one of framing, not substance — both agree it is non-blocking.

**Severity:** Low (Informational per Reviewer 1)

**Assessment:** Not a meaningful risk to the deployment's security controls, but a real (if minor) degradation of log forensics. Both reviewers verified that `requestIP` feeds exclusively into structured log metadata and is never used for authorization, rate limiting, or allowlisting, so header spoofing cannot influence any access-control decision. Reviewer 1 additionally verified there is no log-injection vector: header values must parse as valid IPs via `netip.ParseAddr` before being logged, so arbitrary strings and control characters are discarded. Reviewer 2's framing as an audit-log integrity concern is slightly more apt, since spoofed attribution could matter during incident response — hence Low rather than purely Informational. Both reviewers recommend the same mitigation: override `TRUSTED_PROXY_NETWORKS` with only the exact CIDRs of the deployment's actual reverse proxy.

### Secret-provider propagation to API-triggered scheduled jobs (examined and cleared)

**Description:** Passing the secret provider into `scheduler.TriggerNow` is security-sensitive on its face, as it makes resolved external secrets available to API-triggered job runs.

**Flagged by:** Both reviewers examined this change; neither considers it a risk.

**Severity:** Informational

**Assessment:** Not a real risk. Both reviewers verified the guardrails: the caller must pass the existing API-key check (`ValidateApiKey`), API endpoints are not registered at all unless `API_SECRET` is set, the caller can only select an already-discovered scheduled job, and the provider is the application's already-initialized provider — not request-controlled. The automatic cron scheduler already receives the same provider, so this restores parity rather than creating a new privilege boundary. Reviewer 2 additionally confirmed that resolved values flow only into the scheduled Compose interpolation environment (the feature's documented purpose) and are neither logged nor sent to any new destination.

## Reviewer Agreement

The two reviewers are in near-complete agreement: both confirmed no dependency changes, no new elevated permissions or system access, no backdoor or exfiltration indicators, correct trust-gating semantics in the IP-resolution code, and proper authentication guarding the scheduler fix, and both approved the release. The only divergence is framing of the shared trusted-proxy finding — "informational caveat" (Reviewer 1) versus "non-blocking audit-log integrity concern" (Reviewer 2) — and methodology: Reviewer 1 verified the automated sync provenance and absence of log injection, while Reviewer 2 explicitly verified the merge base, ran `git diff --check`, and noted that builds/tests were intentionally skipped per the mandated read-only review.

## Verdict

**SAFE WITH NOTES** — Both reviewers independently approved this release: a logging-quality feature with correct trust semantics, an authenticated regression fix for secret resolution, and cosmetic build/CI cleanup, with zero dependency changes and no indicators of compromise. The single note is operational hardening: narrow `TRUSTED_PROXY_NETWORKS` from the permissive private-range default to the actual reverse proxy's CIDR to preserve trustworthy source-IP attribution in logs.
