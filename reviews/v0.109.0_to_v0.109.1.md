## Summary of Changes

This is a single upstream patch release comprising two commits and 12 modified files (+543/−256 lines), with roughly 400 of the changed lines being table-driven unit tests. Both reviewers confirmed there are no new, deleted, binary, renamed, or permission-changed files, and Reviewer 2 verified that `origin/main` is the exact merge base of the reviewed HEAD.

The core change reworks how scheduled Compose jobs re-resolve their configuration and external secrets at run time. Previously, doco-cd JSON-encoded external secret *references* (provider-ready identifiers, not secret values) into a `cd.doco.job.external_secret_refs` label on every deployed container so the scheduler could re-resolve them later. That label is now removed. Instead, when a scheduled job fires, the scheduler reconstructs the repository path from the container's deployment labels (source URL, deployment name, config target, git ref), reloads the deploy config from the git checkout under doco-cd's data mount, re-loads `.env` files and profiles, and resolves external secrets based on what the repository configuration declares.

The release also improves one-off container handling: one-off scheduled containers are now stamped with `cd.doco.job.ephemeral=true` plus standard Compose attribution labels, and the scheduler additionally recognizes Compose's native `com.docker.compose.oneoff=true` marker so such containers are not re-discovered as standalone scheduled jobs or flagged as drift.

Housekeeping changes include a Go toolchain bump from 1.26.5 to 1.26.6 (in `go.mod` and the digest-pinned Dockerfile builder image), an updated pinned commit for the existing official `github/codeql-action/upload-sarif` GitHub Action (still hash-pinned, no permission changes), and minor log-message adjustments in the API trigger handler with API-key validation and request authorization unchanged.

## Dependency Review

No new dependencies were added. Both reviewers independently confirmed that `go.sum` is completely untouched and the only `go.mod` change is the toolchain directive bump to 1.26.6. Reviewer 1 additionally noted that the deploy flow actually *removes* one internal import path and adds only imports of the project's own internal packages. The Docker builder image remains the official digest-pinned `golang` image, and the CI action change remains digest-pinned to the existing official CodeQL action. No suspicious network, cryptography, execution, or credential-handling packages were introduced. No dependency risk.

## Security Findings

Neither reviewer found any malicious code, backdoor, vulnerability, or exfiltration path. The entries below are informational observations both reviewers considered security-relevant, plus one review limitation.

### Removal of secret references from container labels (security improvement)

External-secret references are no longer serialized into Docker container labels; they are loaded from deployment configuration in the git checkout and resolved at run time.

- **Flagged by:** Both reviewers, in agreement.
- **Severity:** Informational (positive change).
- **Assessment:** Not a risk — the opposite. Reviewer 1 explains the old design exposed encoded secret-manager references via `docker inspect` to anything with Docker API read access, and meant the scheduler trusted container labels as the source of which secrets to resolve, so a rogue container could forge that label to get arbitrary secret references resolved into an environment. The new design anchors trust in doco-cd's own git checkout, shrinking both the disclosure surface and the label-forgery surface. Reviewer 2 concurs, rating secret handling "improved" and finding no practical new cross-deployment secret-injection path within the existing trust model.

### Filesystem paths constructed from container-label data

The scheduler now builds filesystem paths from container-label values (repository URL, working directory) to locate the deploy config.

- **Flagged by:** Both reviewers; both concluded the access is properly constrained.
- **Severity:** Informational.
- **Assessment:** Not a real risk. Reviewer 1 verified the guards in detail: the repo path is joined under the configured data mount and passed through the pre-existing `VerifyAndSanitizePath`/`InBasePath` checks (`filepath.Rel` plus `..` prefix check, judged sound), and the repository-root walk-up loop resolves symlinks first and refuses to leave the data mount. A forged label can therefore only point at repositories doco-cd has already checked out — no path traversal into the host. Reviewer 2 independently confirmed source paths are sanitized beneath `DATA_MOUNT_PATH` and that symlink-resolved root discovery is limited to that mount.

### Pre-existing trust boundary: Docker API actors can trigger scheduled runs

Any actor able to create containers carrying doco-cd job labels can cause scheduled runs to fire.

- **Flagged by:** Reviewer 1 explicitly, as a pre-existing condition; Reviewer 2's compatible framing is that deployment metadata labels are installed by doco-cd itself rather than accepted from repository-authored service labels.
- **Severity:** Informational (pre-existing, not introduced by this release).
- **Assessment:** Not a new risk. Such an actor already has Docker API access and therefore effectively full host control; this diff does not widen that boundary. Reviewer 1 notes the ephemeral/one-off detection change actually narrows what the scheduler will pick up, and Reviewer 2 confirms no new Docker API operation or permission was introduced.

### Limitation: no byte-for-byte verification against the upstream tag

- **Flagged by:** Reviewer 1 (Reviewer 2 did not perform or mention upstream-tag verification either).
- **Severity:** Informational.
- **Assessment:** Reviewer 1's sandbox blocked all network access, so the vendored tree could not be diffed against the upstream `v0.109.1` tag. Mitigating this, the sync commit follows the repository's established `[Auto] Sync source code` automation pattern, the full local diff was read by both reviewers, and nothing in it is inconsistent with a legitimate upstream patch release.

## Reviewer Agreement

The two reviewers are in near-complete agreement: both delivered an unqualified "safe to build and deploy" verdict, both confirmed zero dependency changes, both characterized the removal of secret references from container labels as a security improvement, and both independently verified that the new label-derived filesystem access is constrained to the data mount. Their differences are ones of emphasis only: Reviewer 1 went deeper on the path-traversal guard mechanics, the label-forgery threat model, and the upstream-verification limitation, while Reviewer 2 contributed exact commit-level scope verification (merge base, file counts, no mode changes) and noted that scheduled runs may now revisit configured Git/OCI resources at execution time — a change in *when* existing authorized functionality runs, not a new network channel. Neither reviewer contradicted the other on any point.

## Verdict

**SAFE** — Both reviewers independently concluded this patch release contains no malicious code, no new dependencies, and no new attack surface, and that its main behavioral change (moving secret-reference resolution off container labels and into the git-anchored deploy config) is a net security improvement with correctly implemented path constraints.
