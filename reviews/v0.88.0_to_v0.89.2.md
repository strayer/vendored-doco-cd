# Security Review: doco-cd v0.88.0 -> v0.89.2

## Review Metadata

| Property | Value |
|----------|-------|
| Upgrade path | v0.88.0 -> v0.89.2 |
| Review date | 2026-06-01 |
| Reviewer 1 | Claude Code 2.1.158, model claude-opus-4-7, effort xhigh |
| Reviewer 2 | Codex codex-cli 0.135.0, model gpt-5.5, reasoning effort xhigh |

## Summary of Changes

This release is dominated by the introduction of **first-class OCI artifact support** as an alternative to git-cloned repositories. A new backend in `internal/source/oci/` pulls artifacts via `google/go-containerregistry`, validates the resolved digest against an expected digest, extracts tar layers into the per-stack internal path, and enforces a `doco.v1` layout. Optional Sigstore-based signature verification is provided through `sigstore/cosign/v3`, supporting both public keys and keyless/OIDC identities.

Trust-policy plumbing is added throughout: `OCI_TRUST_POLICY[_FILE]`, `OCI_VERIFY_MAX_WORKERS`, and a per-deploy `oci:` override. A new OCI webhook provider (`X-Doco-OCI-Signature-256` / `X-Doco-OCI-Event`) reuses the existing HMAC-SHA256 verification path, with a new JSON payload schema (`source/digest/artifact`). The pipeline is refactored around a source-type abstraction: `RepositoryData.SourceUrl` replaces `CloneURL`, polling/webhook handlers branch on `SourceType`, and container labels are renamed from `cd.doco.repository.*` to `cd.doco.source.*` (with legacy compatibility kept on the cleanup side).

Other notable changes include git repair logic (`internal/git/repair.go`) that detects ref/object corruption and falls back to `os.RemoveAll` + re-clone; per-stack locking replacing the global scheduler/deploy mutex; an auto-discovery cache keyed by repo-root + HEAD + scan parameters; and a richer `AutoDiscoveryConfig` (now including `remove_volumes`, `remove_images`). Poll intervals become `time.Duration` rather than integer seconds, and the deployer now waits for in-flight scheduled jobs before redeploy.

Build/CI plumbing adds the official `docker/buildx-bin:0.34.1` plugin (digest-pinned) to the release image — required because compose v5 drives BuildKit — and refreshes GitHub Actions SHA pins. The dev compose file enables OCI polling against `ghcr.io/kimdre/doco-cd_tests:test`.

## Dependency Review

Three modules are newly promoted to direct requires: `github.com/sigstore/cosign/v3 v3.0.6`, `github.com/google/go-containerregistry v0.21.5`, and `github.com/golang-jwt/jwt/v5 v5.3.1` (previously indirect). All three are mainline, widely used projects appropriate to the OCI/signature feature.

Cosign pulls in a broad transitive graph including `sigstore/rekor`, `sigstore/rekor-tiles/v2`, `sigstore/sigstore-go`, `sigstore/timestamp-authority/v2`, `theupdateframework/go-tuf`, `transparency-dev/merkle`, `digitorus/pkcs7`, `digitorus/timestamp`, `ThalesIgnite/crypto11`, `miekg/pkcs11`, `letsencrypt/boulder`, `coreos/go-oidc/v3`, GitLab/GitHub clients, and a large set of `k8s.io/*`, `go-openapi/*`, and `cloud.google.com/go/*` modules. Both reviewers agree the graph is broad but expected when adopting cosign, and neither identified any obscure or suspicious additions. Bumps of pre-existing dependencies (`go-git/v5`, `docker/cli`, `aws-sdk-go-v2/*`, `hashicorp/vault/api`, `compose-spec`, `crypto`, `net`, `oauth2`, `protobuf`, etc.) are point releases from established maintainers. The `docker/buildx-bin` runtime copy is pinned by digest.

## Security Findings

### 1. Artifact-contained OCI config can disable its own signature verification

- **Flagged by:** Codex only (High). Re-reviewed against the published trust-policy documentation, which intentionally supports per-deployment overrides; the issue is specifically that an override loaded from the OCI artifact can govern verification of that same artifact.
- **Severity:** High in this review; later published by the maintainer as Medium in GHSA.
- **Disclosure / fix status:** Disclosed to the maintainer and published as [GHSA-5rv3-qpp3-6jp5](https://github.com/kimdre/doco-cd/security/advisories/GHSA-5rv3-qpp3-6jp5), "OCI Trust Policy Bypass via Artifact-Contained Configuration". The advisory classifies the issue as Medium (`CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:U/C:N/I:H/A:H`, score 6.5), affects `doco-cd` container images `<= 0.90.0`, and credits `strayer` as finder. Fixed in [v0.90.1](https://github.com/kimdre/doco-cd/releases/tag/v0.90.1) via [PR #1407](https://github.com/kimdre/doco-cd/pull/1407), which treats artifact-contained `.doco-cd.yml` as untrusted for trust-policy override decisions and prevents `oci.verify: false` from downgrading globally enabled verification.
- **Description:** The OCI artifact is pulled and extracted in `cmd/doco-cd/handler.go:169` before the deployment config is read from the extracted artifact at `handler.go:213`. That config contains `Oci config.OciTrustPolicyOverride` (`internal/config/deploy/deploy.go:68`) which is then passed into verification at `internal/stages/stage_1_init.go:76`. `EffectiveOciTrustPolicy` in `internal/config/oci.go:51` allows `override.Verify` to replace the global `enabled` setting. If an attacker has write access to a configured OCI artifact tag, but does not control the trusted signing key or OIDC identity, they can publish an unsigned or wrongly signed artifact whose `.doco-cd.yml` contains `oci: { verify: false }`. In that case, the artifact can bypass an administrator's globally enabled `OCI_TRUST_POLICY`. The same trust-boundary problem applies to artifact-supplied public keys/keyless identities, because unverified content should not define the policy used to verify itself.
- **Attack preconditions:** This is not a generic unauthenticated remote-code-execution issue. The attacker needs the ability to publish or retag the OCI artifact that doco-cd is configured to consume, for example via a leaked registry/package token, compromised registry account, or overly broad GHCR write access. The security impact is that registry write access becomes deployment authority even though the configured trust policy is supposed to require a separate trusted signer, such as a specific GitHub Actions OIDC identity.
- **Assessment:** Confirmed by reproduction and maintainer advisory. Trusted operator-owned overrides, such as inline `POLL_CONFIG` deployments, are documented and expected. The unsafe path is artifact-contained `.doco-cd.yml` weakening or replacing the policy before the artifact has been verified. The v0.90.1 fix matches the review's suggested direction: trust-policy data from artifact contents can no longer weaken a globally enabled verification policy.

### 2. OCI polling can race on a shared extraction directory

- **Flagged by:** Codex only (High). Claude Code did not surface this.
- **Severity:** High
- **Description:** OCI repository names intentionally drop the tag/digest in `internal/source/oci/service.go:45`, and `handler.go:93` uses that repository-only name as the `/data` path. `PullAndExtract` removes and rewrites that directory at `service.go:97`. Polling now calls the runner directly without the old per-repository lock (`cmd/doco-cd/handler_poll.go:91`). Two OCI poll configs for different tags in the same repository can therefore concurrently write the same extracted directory; because signature verification happens later, one job can verify digest A while deploying files overwritten by job B — a content-integrity/TOCTOU issue in the trust path.
- **Assessment:** Plausible and concerning given Codex's specific code references. Claude's Finding #2 notes that unverified bytes briefly live on disk but assumes confinement to a per-stack directory; Codex's analysis shows that "per-stack" is actually keyed by repository name without tag/digest, undermining Claude's assumption. Codex's reasoning is more convincing here. Suggested fix: extract to a per-job or per-digest directory and verify there before deploying, or serialize the full pull/extract/verify/deploy sequence per OCI repository path.

### 3. OCI signature verification is opt-in by default

- **Flagged by:** Claude Code (Informational). Not raised by Codex.
- **Severity:** Informational
- **Description:** `OciTrustPolicy.Enabled` defaults to `false` in `parseOciTrustPolicy` (`app_config.go`), and `VerifyWithCosign` is a no-op when disabled. The new OCI-source path will pull and deploy any artifact from any registry the keychain can authenticate to unless an operator sets `OCI_TRUST_POLICY` or a trusted per-deployment override. This is documented as a deliberate design choice.
- **Assessment:** Real but design-by-intent. Operators using OCI artifacts for production deployment bundles should enable the policy globally or in trusted inline deployment config. Note that this finding compounds with Finding #1 only when the deployment config is loaded from the unverified OCI artifact itself.

### 4. Unverified artifact bytes are written to disk before verification

- **Flagged by:** Both reviewers, with differing emphasis. Claude (Informational, Finding #2) treats this as safe because path traversal is enforced and contents aren't executed by doco-cd itself. Codex notes the same ordering but additionally observes there is no visible total extracted-size limit, so an unsigned artifact can still write to or fill `/data` before being rejected.
- **Severity:** Low / Informational
- **Description:** `handle()` calls `oci.PullAndExtract` before stage 1 runs `VerifyWithCosign`. The expected-vs-pulled digest is checked at pull time, `io.CopyN` is bounded by the tar header size, path traversal is enforced via `filesystem.InBasePath`, and `extractTarStream` only handles `TypeDir`/`TypeReg` (silently skipping symlinks/hardlinks/device nodes).
- **Assessment:** Containment is reasonable, but Codex's point about the absence of an overall extracted-size cap is valid — an attacker who can publish artifacts could exhaust disk before signature rejection. Worth a size limit as a defense-in-depth measure. Note this finding is largely subsumed by Findings #1 and #2, which are the more impactful manifestations of the extract-before-verify ordering.

### 5. Tar layer permissions preserved from header

- **Flagged by:** Claude Code (Informational, Finding #4). Not raised by Codex.
- **Severity:** Informational
- **Description:** File modes from the tar header are applied via `os.FileMode(uint32(h.Mode&0o777))` in `service.go`. A malicious artifact could create world-writable files inside the extracted artifact directory.
- **Assessment:** Limited practical impact since the path is confined and the artifact contents aren't executed by doco-cd itself. Noted as an observation, not a finding requiring action.

### 6. OCI webhook authentication

- **Flagged by:** Claude Code (Informational, Finding #3). Not separately raised by Codex.
- **Severity:** Informational
- **Description:** `X-Doco-OCI-Signature-256` is parsed by the same `verifySignature` HMAC-SHA256 helper as GitHub/Forgejo and is gated by `WEBHOOK_SECRET`. The OCI payload requires `source: "oci"` and is parsed with `name.ParseReference` for the artifact URL — no command/template interpolation.
- **Assessment:** No new bypass path; webhook handling extends the existing trusted pattern.

### 7. `RepairRepository` performs `os.RemoveAll`

- **Flagged by:** Claude Code (Informational, Finding #5). Not raised by Codex.
- **Severity:** Informational
- **Description:** The path is derived from deploy config / internal storage layout, never from webhook/OCI input. The function only triggers when go-git reports corruption indicators. The lock is dropped before removal and re-acquired via the path lock inside `CloneRepository`.
- **Assessment:** Bounded blast radius; acceptable.

### 8. Buildx plugin and CI action pin updates

- **Flagged by:** Claude Code (Informational, Findings #6 and #7). Both reviewers agree the buildx-bin addition is digest-pinned and from an official source.
- **Severity:** Informational
- **Description:** `docker/buildx-bin:0.34.1` is copied into the release image, digest-pinned. All `uses:` bumps in `.github/workflows/*.yaml` are SHA-pinned to new commits of the same official actions; no new third-party actions introduced. Privilege envelope unchanged (the container already mounts `/var/run/docker.sock`).
- **Assessment:** No concerns.

### 9. No suspicious code patterns or new outbound endpoints

- **Flagged by:** Both reviewers concur.
- **Severity:** Informational
- **Description:** No new `exec.Command`/`os.Exec*` over untrusted input; no eval/template execution over external data; no filesystem writes outside per-deployment scratch directories; no changes to credential plumbing apart from a `signin` package version bump. Cosign brings in TUF + Sigstore public-good connectivity, but only when an operator opts into verification (`loadTrustedRoot` is only invoked from `VerifyWithCosign`, which short-circuits when the policy is disabled). No telemetry, callback URLs, or hard-coded external addresses observed. Neither reviewer found evidence of a classic backdoor, hardcoded exfiltration endpoint, new privileged container setting, or unexpected host mount.
- **Assessment:** Clean.

## Reviewer Agreement

The two reviewers agree on the overall shape of the release, on the cleanliness of the dependency graph, on the absence of backdoors/exfiltration/privileged-mount changes, and on the soundness of webhook handling, the git-repair logic, and CI pin updates. They diverge on the OCI verification flow: Claude treats the extract-before-verify ordering as safe due to path confinement and stops there, while Codex traces the deploy-config override path back into the verification policy itself (Finding #1) and observes that the shared extraction directory is keyed only by repository name without tag/digest (Finding #2). After re-reading the trust-policy documentation, Finding #1 should be understood as a conditional verification-bypass issue: per-deployment overrides are intentional, but artifact-supplied overrides should not be able to weaken verification of the artifact that supplies them. The finding was later disclosed to the maintainer, published as GHSA-5rv3-qpp3-6jp5, and fixed in v0.90.1.

## Verdict

**CONDITIONALLY UNSAFE FOR OCI TRUST ENFORCEMENT IN v0.89.2** — Git-only deployments appear unaffected, and this is not a blanket unauthenticated vulnerability. For operators relying on OCI signature verification to separate "can push to registry" from "is an approved signer", Finding #1 is a meaningful bypass: an attacker with write access to the watched OCI tag can make an unsigned or wrongly signed artifact disable its own verification. Finding #2 further weakens digest/content binding when multiple OCI tags from the same repository can be processed concurrently. Operators not using OCI sources are not affected; operators using OCI sources without signature verification are accepting the documented opt-in trust model. Finding #1 was disclosed and fixed in v0.90.1; operators using OCI signature verification for production deployment bundles should upgrade to v0.90.1 or later.
